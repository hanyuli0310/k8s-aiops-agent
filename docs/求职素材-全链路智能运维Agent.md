### 2.1 一段话概述

面向生产 K8s 集群（`prod-cluster-01`）的对话式智能运维 Agent。用户用自然语言提出运维诉求，Agent 自主完成多步排查并给出带证据的结论与可执行治理方案，确认后执行并自动复扫验证。核心是一套**自研的非 workflow Agent Harness**——不把流程写死成图，而是由模型在 ReAct 循环中自主决策下一步动作，Harness 负责运行时治理（预算、权限、上下文、幻觉、续跑）。

### 2.2 业务问题

一次线上告警，SRE 的真实工作流是：在**云监控指标、日志服务、链路追踪、K8s 资源快照**四类系统间反复跳转，人工做时间对齐与因果关联，最终依赖个人经验判断根因。问题在于：

- **上下文割裂**：证据分散在 4 个系统，关联全靠人脑；
- **经验依赖**：同一现象，资深与新手给出的根因可能完全不同；
- **闭环断裂**：定位到根因后，治理动作的执行与效果验证又是一轮手动操作。

### 2.3 解决方案与能力闭环

| 阶段 | Agent 做的事 | 关键产出 |
|---|---|---|
| 数据采集 | 双通道采集（定时 60s 拓扑类高水位增量 + 实时 10s 水位类） | 7 张表入库，行数与标准答案对账 |
| 拓扑梳理 | 从调用链数据反推服务依赖 | G6 拓扑图，病灶边标红 |
| 风险扫描 | 13 类内置规则，P1/P2 分级 | 每条风险带证据与治理建议；规则未覆盖的异常引导 Agent 用通用三步自查 |
| 故障定位 | 多步 ReAct 自主排查 | **根因链**（如 `API-001 ← DB-002 ← DB-001`）+ 复合索引方案 |
| 治理闭环 | 生成 check 列表 → 人工确认 → 执行 → 复扫 | 风险状态转 resolved |

**闭环的真实性**（区别于「假闭环 demo」的关键）：治理动作通过 Action 反馈**真实改变了被管世界的状态**——连接使用率从 92% 自然回落到 54%，指标滑窗过后风险自动转 resolved，而不是把状态硬置成「已解决」。

### 2.4 系统架构（四进程）

```
mock_server (:9001)      世界状态模拟器：5s/拍状态机，可注入故障 + 反向 BFS 传播
      ↓ 阿里云格式接口（CMS / SLS / K8s）
data_collector           独立采集进程：定时 60s + 实时 10s 双通道
      ↓ 落库
backend (:8000)          FastAPI + Agent Harness（16 模块 / 8 Agent / 22 工具 / 13 规则 / 8 Skill）
      ↓ SSE 事件流
frontend (:5173)         React 18 + G6：对话 Tab + 运维控制台 Tab + Skill/Agent 资产面板
```

> 为什么自建世界模拟器：需要一个**可复现、可注入故障、且治理动作能真实生效**的被管环境来验证闭环。它由状态机驱动、指标由基线+噪声+故障效应+动作效应合成，保证「注入故障 → 指标异常 → 治理 → 指标回落」是数据驱动的因果链，而非脚本演出。
>
> 落地成本：对接真实生产环境只需替换采集器的数据源客户端与治理工具实现，Harness 层无需改动。

## 三、核心机制（算法侧深挖）

> 面试时不必全讲，挑 3~4 个深入。推荐组合：**上下文工程 + 幻觉治理 + 预算语义**——这三个最能体现算法岗需要的"模型能力边界感"。

### 3.1 顶层调度：从硬编码意图路由到模型自主编排（对齐 Claude Code）

这一层经历过一次**架构级重构**，也是面试里最能聊的点之一。

**旧方案（预制意图 + 硬映射）**：先用 LLM 把用户请求分类到 9 个预制意图，再按一张硬映射表选一个 Agent，全面体检走写死的三阶段串行。**两层都是人定的**：预制意图覆盖不住真实请求分布（“先看拓扑再对比两个库的水位”归不到任何意图），而“派几个 Agent、串行还是并行”也是写死的。

**新方案（对齐 Claude Code）**：取消意图分类，请求直接交给一个持全部工具 + `dispatch_agent` 的**编排 Agent**，由模型自己决定派几个子 Agent、串行还是并行。Claude Code 根本没有意图分类层，这是调研其实现后的候选结论。

- **保留意图路由作为降级归路**：无 API Key / LLM 不可用时，退化为关键词正则路由 + 脚本化流程，离线仍可演示；model 模式下意图降为**零 LLM 的关键词**，仅用于前端展示，顺带省掉一次串在等待路径上的快模型往返。
- **用同一套评测实测对比**（而不是拍脑袋说“模型自主更好”）：同一次故障注入下两种调度各排障多次取中位数，**模型自主编排 6/6 优于预制意图 5/6，定论为默认调度**。
- **一个值得讲的坑**：编排 Agent 提示词第一版把“子任务彼此独立”写成了派子 Agent 的理由，模型据此并行派了两个子 Agent → 耗时/成本暴涨 11 倍。实际上**独立性只决定能不能并行，不决定要不要派子 Agent**——主 Agent 自己的工具调用本来就能并行，子 Agent 的价值是上下文隔离而非并行加速。改提示词后同一请求从 394s 降到 34.5s。

### 3.2 上下文工程：Skill 三层渐进式披露

**问题**：早期把整篇 Skill 文档拼进系统提示词，3 篇时尚可，扩到 8 篇后常驻成本超 5000 token，而大部分轮次根本用不到那些内容。

**方案**（对齐 Claude Code 的 `loadSkillsDir` 实现思路）：

| 层 | 内容 | 加载时机 | 体量 |
|---|---|---|---|
| L1 | frontmatter：name / description / when_to_use | **常驻**系统提示词 | 每篇约 50 token |
| L2 | SKILL.md 正文 | `load_skill(name)` 按需 | — |
| L3 | `references/*.md` 深度细则 | `load_skill(name, reference=...)` 按需 | — |

**量化收益**：常驻目录 1009 字符 / 全量知识 23953 字符 = **常驻占比仅 4.2%**。

**一个刻意的偏离**（体现设计分寸感）：Agent 的**主 Skill 仍注入正文**，而非只给 L1。因为 RiskAgent 的治理方法论是它每轮都要用的核心知识，若要求它先调一次 `load_skill` 才能拿到，等于给每个治理请求多加一轮 LLM 往返。把细节下沉到 L3 后主体已经很薄，这个折中代价很小。

### 3.3 上下文压缩：三级阶梯 + 数值保真

**压力度量**：取「字符占比」与「token 占比」的**较大者**——两种口径都可能先触顶，取大值才不会漏。

| 级别 | 手段 | LLM 成本 |
|---|---|---|
| L1 微压缩 | 裁剪冗余结构、丢弃低信息量片段 | **零** |
| L2 中段摘要 | 快模型摘要历史中段，保留首尾 | 1 次快模型 |
| L3 紧急压缩 | 超窗口时的兜底压缩 + 重试 | 1 次 |

**数值保真兜底**：摘要必然丢信息，但**关键度量值不能丢**。压缩后比对压缩前的数值集合，把丢失的关键数值以补录形式追加回上下文。

> 这里踩过一个值得讲的坑：补录时用 `f"{v:g}"` 格式化，把 `1162951` 写成了 `1.16295e+06`——模型对不上工具返回的原值，且精度真的丢了。**用一个会改写数值的格式化函数做「保真」补录，等于自相矛盾**。改为按整数/小数分别精确格式化。

### 3.4 幻觉治理：证据池事实核对

**核心定义**：证据池 = **模型实际看到过的全部文本**（工具返回的预览内容、用户输入），而非数据库里客观存在的所有数据。这个定义是整个机制的关键——模型只可能"看到过"的东西才算它的依据。

**分级策略**（体现"知道什么该管、什么不该管"）：

| 类别 | 判定 | 处置 | 理由 |
|---|---|---|---|
| A1 | hex 标识符不在池中 | **报警 + 自纠正** | trace_id 这类不可能被推算出来，不在池中即为凭空生成 |
| A2 | 连字符资源名不在池中**且编辑距离 ≤ 2** | **报警 + 自纠正** | 只报"近似但不相等"——典型的记错实例名 |
| B | 关键数值不在池中 | **仅统计，不报警** | 单位换算（336500μs → 336.5ms）、聚合、四则运算都是**应该鼓励**的行为，硬拦截必然高误报 |
| C | 某份工具结果的数据最新时间 >30min 前且回答在说“当前” | **自动重查最新数据复核**（并写明“已用最新数据复核，结论X”）；数据源停更时降级为告警 | 时效维度：推理层看不出“把一小时前的数据当成当前”，因为引用的数据都真实存在 |

**"什么算关键数值"的口径**：**有小数部分的一律算**（P99 `1.244s`、错误率 `1.78%` 恰恰是最该核对的），纯整数则要求绝对值 ≥ 11（滤掉序号、条数这类必然出现的小整数）。数值匹配支持单位换算、四舍五入与**中文量级约等**（模型说"116 万"、池里是 `1162951`，相对误差 < 1% 即命中；容差刻意收窄到 1%，放开会让任意两数互相匹配、指标失去意义）。

**效果**：真机多场景评估 **A 类零误报**（核对量 90 个数值全部命中）；C 类在真机抛障评测中报对，揭出“把一小时前的数据当成当前”的取数缺陷。

### 3.5 并行子 Agent 与预算语义

- **并行执行**：实测峰值并发 2，耗时 0.61s vs 串行 1.2s。
- **上下文隔离**：子 Agent 独立上下文，只把结论回传父级，避免中间过程污染主上下文。
- **预算语义**（最值得讲的设计）：子 Agent 有**独立的预算上限**（防单个跑飞），但**消耗向父归集**（保整轮封顶）。实测抓到过「子 Agent token 不计入父预算」的缺陷——整轮实际开销可能突破用户设定的上限。
- **中断收口**：超预算/被中断时**带回部分结论**（用已积累的思考与中间结果拼装，**零 LLM 调用**——触发原因往往就是预算耗尽，再花一次往返自相矛盾）。修这个缺口的直接动因：原来父 Agent 只拿到一句"[子 Agent aborted]"，什么都用不上，于是倾向于原样重派，真机白烧过 40435 token。

### 3.6 任务清单与分段续跑

`MAX_AGENT_STEPS` 是**单段**上限而非全局上限。续跑需通过**三道闸门**（顺序有意义）：

1. **预算优先**——超预算或被中断时绝不续跑；
2. **续跑次数上限**；
3. **结构化的未完成信号**——任务清单里存在非 done 步骤。没维护清单时不猜、不问模型"你做完了吗"，直接交回用户决定。

> **关键不变量：续跑只重置步数，绝不重置预算**。否则"上限"形同虚设。

### 3.7 权限门禁与审计

三态模式（`readonly` / `confirm` / `auto`）+ 阻塞式确认 + 全量审计。**auto 采用白名单而非黑名单**：只有显式标注为写业务数据的工具才自动放行，避免未来新增的写工具被静默允许。

### 3.8 评测方法：量化评测 + 变异测试 + 评测自省（算法岗重点）

这一块是整个项目里**最能体现工程严谨度**的部分，面试建议重点展开。

**一、量化评测框架（L1/L2 双层）**。自建一套面向排障质量的评测，两条原则：

- **真值一律从运行中的环境取，评测端不复制**（复制必漂移）；**判定机械可复现，判不准的指标就不做**。
- 为评测专门设计了 12 个注入故障场景，含**同型不同实例**（测串报）、**易混淆对**（缓存雪崩 vs 数据库故障，测推理而非套模板）、**负样本**（测误报）。
- 结果：规则侧 12 场景 P/R/F1 均 **100%**（tp=23 fp=0 fn=0）、实例定位 11/11、串报 0；集群规模**分两次扩到 32 倍**（100 节点 / 300 服务 / 603 实例 / 74 接口）后重跑全部场景，仍 **0 误报 0 漏报 0 串报**、规则扫描耗时仅 0.03s→0.05s——候选池从 19 涨到 603，"实例定位 100%" 才真正有说服力。

**二、用「朴素基线」对照臂科学量化 Harness 的真实增量（面试最推荐展开）**。这是我认为整个评测里最有含金量、也最能体现科学态度的一步：

- **对照怎么设**：`HARNESS_PROFILE=naive` 臂 = 同一个模型、同一批业务工具、同样步数上限、同样环境描述，**只**剥离掉方法论准则 / 事实核对 / 并行取数 / 子 Agent / 分段续跑。公平性边界由 **9 项常驻测试锁死**（防止有人给基线少配工具或混进方法论把数字做好看）。
- **为什么这么设**：读者真正想问的是“我自己拿大模型接上工具不就行了，凭什么用你这套？”——对照组必须正是这个替代方案。
- **四类任务具体是什么**（被追问时能逐条答出来，比只说"四维度"可信得多）：

  | 维度 | 任务内容 | 考察什么 |
  |---|---|---|
  | **强干扰**（最贴近生产） | 同时注入**三个独立故障**（缓存雪崩 + 慢查询风暴 + Pod OOM），要求分别定位各自根因、说清有几个互相独立的故障、给出治理先后顺序 | 会不会把独立故障**串成一条因果链**。这是四类里唯一需要几十步排查的场景（完整臂 46 次工具调用），也是耗时差距最大的（1276s → **635s**，快一半） |
  | **长任务** | 五段式体检：①梳理拓扑指出异常边 ②扫描风险按 P1/P2 分级 ③每条 P1 用真实数据说明当前水位 ④⑤治理与优先级 | 长程任务里**前面的结论会不会被后面丢掉**（上下文压缩的数值保真） |
  | **大数据量** | 统计最近 30 分钟全部 5xx：总条数 + 按接口分组的 Top N，要求**准确数字** | 面对数千条日志会不会**估算或编数**。差距最悬殊：24 次/150s → **8 次/50s（3 倍）** |
  | **易幻觉** | 故障简报：Redis 精确到小数点后一位的 CPU/内存、两台 RDS 各自连接数、**真实 trace_id** | 最易诱发**编造标识符与数值**（专为压垮基线设计，结果基线也没编） |

- **四维度实测**得到一个**反直觉、但我选择如实写进报告**的结论：

  | 维度 | 结论 |
  |---|---|
  | 根因准确率 | **打平 4/4 vs 4/4** —— `qwen3.8-max` 自己就会 Trace 排除、时间对齐、区分独立故障 |
  | 工具调用 | 完整臂一致更少，中位 **-27%**（22→16 次）；四轮观测方向从未反转 |
  | 排障耗时 | 中位 **-20%**（127s→102s），多数场景更快；⚠️ 方差大（同场景四轮 407~1521s），部分长任务上可能更慢 |
  | 数据时效可信度 | 遇到同类问题时：完整臂 **3 处全部告知用户**（告警或自动复核）vs 基线 **11 处全部静默交付** |
  | 变更安全 | 基线拿着破坏性工具**没有任何门禁与审计**，完整臂须经四层门禁 + 用户确认 |

- **这个负结果本身就是贡献**：它把项目卖点从一句站不住的“准确率提升 N 个百分点”（强模型下根本拿不到），修正为可复现、经得起追问的“**同等正确下更省调用 + 结论可信度 + 变更安全**”，并明确划出“任务越复杂越划算、越简单越是负担”的部署边界。

**三、评测的真正价值不是分数，是反咬出的缺陷**。共揭出 **13+ 个真实缺陷**，最典型的一个：

> `query_logs` 无时间窗口且升序返回，拿回库里**最旧**的日志（两小时前另一次演练的残留），Agent 据此报出“三源叠加”的根因——结论完全错，而**它引用的每一条日志都真实存在**，幻觉核对也查不出。修复后复测主根因从错变对。这个发现直接催生了幻觉核对的 **C 类（时效维度）**——它先抓出基线静默交付的过期结论；后来更进一步：给聚合型工具补数据时间窗、并让 Agent 在数据过期时**自动重查复核** —— 实测两臂都会遇到数据过期（完整 4 处、基线 6 处），但完整臂**每一处都告知了用户**，基线一处都没说。

**四、变异测试 + 文档对账**。不满足于“测试通过”，而是故意注入回归看用例是否变红；并对 Skill 文档引用的工具参数/表列名做代码级常驻对账（这类漂移不会报错，只会让模型静默犯错）。

**五、连评测判定逻辑本身也建了回归用例**（最能体现反思的一点）：串报判定曾把两份**正确**的回答（“此前 order 库故障已平息、风险项已 resolved”）判成串报，让我得出“串报是 Agent 推理层弱点”的错结论并写进了报告。根因是排除词表漏了“时态性排除”。修复时又立即出现反方向误判（把真串报放过），因此加了一道否决门并配**双向用例**。

> 核心认知：**指标出错比被测系统出错更糟** —— 系统出错会被指标发现，指标出错会把优化引向不存在的问题。启发式判定不配双向回归用例，就只是一个会说谎的数字。

## 六、使用建议与诚实边界

**投递前请按实际情况调整**：

1. **岗位适配**：本文已按「大模型算法 / Agent 算法」岗调整侧重（上下文工程、幻觉治理、模型选型、评测方法在前；权限审计、CI 这类纯工程项收敛为一条）。若投 AI Infra / 后端，应把权限门禁、并发、可观测性提前。
2. **诚实分工**：这是 3 人 hackathon 项目。Harness 内核与评测体系确实是你的主战场，可以理直气壮作为个人贡献陈述；但面试被问到团队分工时应主动说明队友的部分。
3. **不要夸大部署规模**：被管环境是自建的世界状态模拟器，**不是真实生产集群**。描述时用「面向生产 K8s 集群设计」而非「已在生产环境运行」。这一点如果被追问而含糊，损失远大于收益——而且模拟器本身的设计（状态机 + 故障传播 + 动作生效）也是可讲的技术点。
4. **准备好现场追问**：面试官很可能顺着某个机制深挖实现。第三节每一条都有对应的代码位置，建议投递前重读 `CLAUDE.md`（未随仓库公开） §3，确保能讲到实现细节而非只有概念。
5. **主动讲那个"负结果"，别回避**：基线对照测出"强模型下准确率打平"，这**不是**要藏起来的短板，而是全篇最能体现科学素养的地方——它证明你会设对照、守公平性、并诚实面对不利数据。讲法见 §四 Q9。真正的卖点已经从"准确率提升"稳稳落在"工具调用 -27% + 可信度 + 变更安全 + 清晰的部署边界"上，这些都可复现、经得起追问。**切忌**在简历里同时写"准确率大幅提升"——与报告结论矛盾，一旦被对照追问会非常被动。
