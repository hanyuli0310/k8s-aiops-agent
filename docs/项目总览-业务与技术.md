# 第一部分 · 业务

## 1. 为什么要做这个项目

### 1.1 场景设定

一个运行在阿里云上的电商微服务系统：**300 个服务**、2 台 RDS MySQL、1 个 Redis、**603 个实例**、**74 个对外接口**，部署在生产 K8s 集群 `prod-cluster-01`（cn-hangzhou，**100 节点**跨 3 可用区）。可观测数据分散在四个地方：

- **云监控 CMS**：CPU / 内存 / 连接数 / QPS 等时序指标
- **日志服务 SLS**：Ingress 访问日志、应用日志、RDS 慢查询日志、K8s 事件
- **链路追踪 Trace**：跨服务调用的 span 数据
- **K8s API**：Deployment / Pod / Node 的资源配置快照

### 1.2 真实的排障工作流有多痛

凌晨两点，告警响了：「下单接口 P99 超过 1s」。一个 SRE 要做的事：

1. 打开云监控，看下单服务的 CPU、内存 —— 正常；
2. 切到日志服务，查 Ingress 日志，确认 P99 确实劣化、错误率上升；
3. 切到链路追踪，找一条慢的 trace，逐层下钻，发现耗时集中在数据库调用；
4. 切回日志服务，查 RDS 慢查询日志，找到一条全表扫描的 SQL；
5. 切到 K8s，看这个服务的副本数、资源配额是否有问题；
6. **人工把这五处证据在时间轴上对齐**，判断根因是「缺索引导致慢查询 → 连接堆积 → 接口超时」；
7. 设计索引方案、评估风险、执行、再回到第 1 步验证是否恢复。

整个过程 20 分钟到 2 小时，取决于这个人的经验。

### 1.3 这件事为什么适合交给 Agent

| 环节 | 人的劣势 | Agent 的优势 |
|---|---|---|
| 跨系统取证 | 手动跳转、易漏 | 工具调用，一次拉全 |
| 时间轴对齐 | 靠脑补 | 结构化查询，精确对齐 |
| 因果推断 | 依赖个人经验 | 沉淀为可复用的方法论（Skill） |
| 方案生成 | 经验差异大 | 基于规则细则 + 真实证据推导 |
| 执行与验证 | 又一轮手动操作 | 工具执行 + 自动复扫 |

**关键判断**：这个场景**不适合用 workflow 写死**。同样是「接口慢」，根因可能在索引、连接池、GC、超卖、网络任一环，排查路径无法穷举。必须让模型在循环中自主决定「下一步查什么」——这是我们选择 ReAct 范式与自研 Harness 的根本原因。

## 2. 业务痛点拆解

| # | 痛点 | 具体表现 | 我们的应对 |
|---|---|---|---|
| P1 | **上下文割裂** | 证据分散在 4 类系统，关联全靠人脑 | 统一数据层（17 张表）+ 22 个工具，Agent 一次性取全 |
| P2 | **经验依赖** | 同一现象，资深与新手结论可能完全不同 | 8 篇 Skill 沉淀方法论（五步排查法、治理顺序、索引设计原则） |
| P3 | **闭环断裂** | 定位到根因后，执行与验证又是手动 | 治理动作工具化 + Action 反馈 + 自动复扫验证 |
| P4 | **风险发现滞后** | 配置类隐患（单副本、缺探针、超卖）平时没人查 | 13 类内置规则 + 定时扫描，P1/P2 分级 |
| P5 | **AI 结论不可信** | 大模型会编造 trace_id、记错实例名 | 证据池事实核对机制（第 7.6 节） |
| P6 | **AI 执行有风险** | 让 Agent 直接改生产环境很危险 | 三态权限门禁 + 阻塞式确认 + 全量审计（第 7.7 节） |

> P5 和 P6 是**做了才知道有多重要**的两个痛点。前者关乎结论可信度，后者关乎能否真正上生产——它们是这个项目从「demo」走向「可用」的分界线。

## 3. 我们做了什么：五段能力闭环

```
   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │ 数据采集  │ → │  拓扑梳理  │ → │  风险扫描 │ → │  故障定位 │ → │  治理闭环  │
   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
        ↑                                                            │
        └──────────────────── 复扫验证（数据驱动） ────────────────────┘
```

| 阶段 | 用户怎么说 | Agent 做什么 | 产出 |
|---|---|---|---|
| **数据采集** | 「采集集群可观测数据」 | 调 CMS/SLS/K8s 接口拉数据入库 | 7 张业务表，汇报每表行数与时间覆盖 |
| **拓扑梳理** | 「梳理服务拓扑」 | 从 trace span 反推服务依赖 | G6 拓扑图（8 节点 9 边），**病灶边标红** |
| **风险扫描** | 「做一次全面风险扫描」 | 跑 13 类规则 | 风险清单，每条带 evidence + 治理建议 |
| **故障定位** | 「下单接口很慢，帮我定位」 | 多步 ReAct 自主排查 | **根因链** `API-001 ← DB-002 ← DB-001` + 索引方案 |
| **治理闭环** | 「按你的方案执行，然后复扫」 | 生成 check 列表 → 确认 → 执行 → 复扫 | 风险状态转 `resolved` |

### 3.1 闭环的「真实性」是这个项目的核心主张

很多 AI 运维 demo 的闭环是假的：执行治理动作后，直接把风险状态改成「已解决」。

我们的做法：治理动作通过 **Action 反馈**真实改变被管世界的状态，然后**等指标自然回落**、滑动窗口滑过、复扫时规则**重新判定**为通过。

实测数据：注入 RDS 连接风暴故障后，连接使用率 92% → 执行治理 → **自然回落到 54%** → 窗口滑过 → 风险自动 `resolved`。

> 这个差别很重要：假闭环无法回答「治理动作到底有没有效果」，真闭环才能。

## 4. 核心业务场景走一遍

### 场景：慢查询风暴（最能体现全链路价值）

**第 0 步 · 稳态**：实时图表平稳，风险面板只有 7 条预埋的配置类基线风险。

**第 1 步 · 注入故障**：在运维控制台点「慢查询风暴」。世界模拟器开始产生全表扫描慢查询，并通过**反向 BFS 传播**（每跳衰减 ×0.6）让上游服务也受影响。

**第 2 步 · 自动发现**（≤2 个扫描周期）：定时扫描报告出现新增风险：
- `DB-002` 无索引慢查询（P2）
- `DB-001` RDS 连接使用率 >80%（P1）
- `API-001` 接口 P99>1s（P1）

**关键细节**：`resource_ref` 精确到 `rds-mysql-order`，**另一台 RDS 不误报**——规则按实例分组判定，而非全表聚合。

**第 3 步 · 根因定位**：用户问「下单接口很慢，帮我定位」。DiagnoseAgent 按五步排查法：

```
① 确认现象   query_logs → P99 1.244s，错误率 1.78%
② 定位层级   query_traces → 耗时集中在 DB 调用
③ 深挖数据库 query_logs(slow) → 全表扫描，rows_examined 1162951 / rows_sent 20
④ 排除干扰   query_metrics → CPU/内存正常，排除资源瓶颈
⑤ 输出根因链 API-001 ← DB-002 ← DB-001
```

每步结论都必须有工具返回的真实数值支撑——这是写进 Skill 的硬约束。

**第 4 步 · 治理方案**：RiskAgent 生成 check 列表（复合索引 DDL + 索引列序推导依据 + 风险评估），用户在前端**勾选确认**。

**第 5 步 · 执行与自愈**：Action 传回世界模拟器 → 慢查询消失 → 连接数按**半衰期指数恢复** → 指标回落。

**第 6 步 · 复扫验证**：滑窗滑过后复扫，三条风险全部 `resolved`。

> 治理顺序有讲究：CAP-003（命名空间超卖）必须**最后**处理。实测数据说明原因——把 order-service 扩到 3 副本后，超卖率从 167.95% 反而升到 202.14%（+34.2 个百分点）。这条经验写进了 `risk_governance` Skill。

## 6. 一条消息的完整生命周期

以「下单接口很慢，帮我定位」为例：

```
用户输入
   │
   ▼
① 意图标记（intent.py）              → SSE: intent
   默认（AGENT_ROUTING=model）走**纯关键词**、零 LLM 调用，
   仅用于前端展示与记忆键，事件里 `decides_routing: false` 表明它不决定调度；
   切回 AGENT_ROUTING=intent 时才用 LLM 结构化输出 JSON 并抽取实体、且真正决定路由。
   ⚠️ 无 LLM 时两种模式都降级到关键词正则 + 脚本化流程，保证离线可演示
   │
   ▼
② 调度编排（scheduler.py）           → SSE: agent_start
   INTENT_AGENT 映射：fault_diagnose → DiagnoseAgent
   full_checkup 走多阶段编排（采集→拓扑→扫描）
   │
   ▼
③ Agent 组装（agents/base.py）
   系统提示词 = 通用准则 + Agent 人设 + 主 Skill 正文
              + 其余 7 篇 Skill 的 L1 元信息（仅 1009 字符）
   工具集 = allowed-tools 过滤后的子集（本例 9 个）
   │
   ▼
④ ReAct Loop（loop.py）—— 核心循环
   ┌──────────────────────────────────────────────┐
   │ 每步开头：should_stop() 检查预算/中断          │
   │   └→ 命中则带回【部分结论】再退出（零 LLM）    │
   │ 压力检查：pressure() ≥ 阈值 → 分级压缩        │
   │ 调 LLM  → thinking / tool_calls              │
   │ 权限门禁：危险工具 → 阻塞等待用户确认          │
   │ 工具执行：只读工具可【并行】，写操作串行        │
   │ 大结果落盘：只把预览喂给模型                   │
   │ 证据累积：把模型看到的文本存进证据池           │
   └──────────────────────────────────────────────┘
        循环直到模型不再调工具，或触发闸门
   │      SSE: thinking / tool_call / tool_result / usage
   │           permission_request / subagent_start / plan_update
   ▼
⑤ 结论事实核对（verifier.py）        → SSE: verify_warning
   拿最终回答与证据池比对：
   A1 凭空 hex 标识符 → 报警
   A2 近似资源名（编辑距离 ≤2）→ 报警
   B  关键数值 → 只统计，不报警
   │
   ▼
⑥ 续跑判定（runctx.can_continue）    → SSE: continued
   三道闸门：预算优先 → 次数上限 → 结构化未完成信号
   │
   ▼
⑦ 输出与记忆                         → SSE: answer / done
   长期记忆按意图选择性落库（agent_memory）
```

## 7. Agent Harness：十大机制详解

> Harness = Agent 的**运行时**。它不决定「做什么」（那是模型的事），只负责「怎么安全、可控、经济地跑」。
> 这是本项目技术含量最集中的部分，16 个模块共同构成。

### 7.1 顶层调度：从预制意图到模型自主编排

这一层经历过一次**架构级重构**，两种方式共存且可实测对比（`config.AGENT_ROUTING`）。

#### 旧方式：预制意图 + 硬映射（`AGENT_ROUTING=intent`）

用户请求 → LLM 意图分类（9 类意图）→ `INTENT_AGENT` 硬映射选一个专职 Agent；
`full_checkup` 另走写死的三阶段串行（采集 → 拓扑 → 扫描）。

这个设计有两层都是人定的问题：

1. **预制意图覆盖不住真实请求的分布**。“先看拓扑再对比两个库的水位”归不到任何一个意图，
   只能落到兜底的 general。
2. **即使分对了，“派几个 Agent、串行还是并行”也是写死的**。而拓扑梳理与风险扫描
   完全互不依赖，本可并行。

#### 新方式：编排 Agent 自主决策（`AGENT_ROUTING=model`，默认）

**不做意图分类**，用户请求直接交给 `OrchestratorAgent`（持有全部 21 个工具
+ `dispatch_agent` + 治理工具），由模型自己决定调什么、派几个子 Agent、并行还是串行。
对齐 Claude Code 的做法 —— 它根本没有意图分类层。

意图并未完全下岗，而是**降级为纯关键词（零 LLM 调用）、只做两件事**：
前端展示标签、判定要不要写长期记忆。SSE `intent` 事件多了个 `decides_routing` 字段
告知前端“这个意图是否真的决定了调度”。副作用是省掉一次串在用户等待路径上的快模型往返。

#### 实测对比（详见《量化评测报告》§6.2、§6.5）

跨两个预制意图的请求（“梳理拓扑，同时做一次风险扫描”），开销对比：

| 模式 | 耗时 | 成本 | 实际行为 |
|---|---|---|---|
| model | **34.5s** | **¥0.64** | 自己在同一轮并行发两个工具调用 |
| intent | 76.4s | ¥1.76 | 单 Agent 串行 11 次调用 |

更关键的是**排障准确率**（同一故障注入下两种调度各排障多次，取中位数）：

| 维度 | model | intent |
|---|---|---|
| 根因严格通过 | **6/6 = 100%** | 5/6 = 83% |
| 耗时中位数 | **38.9s** | 47.2s |
| 同型实例串报 | **0** | 1 次（把另一台库当成“触发源”） |

> **结论：确认 `model` 为默认调度**。把“派几个 Agent、串行还是并行”的决策权交给模型，
> 准确率更高、耗时更低、且未损害排障质量。保留 `intent` 的价值不是它更好，
> 而是：(1) 无 LLM 可用时的降级归路；(2) 可对比基准。

#### ★ 重构中学到的一件事：“多 Agent 并行”不等于快

编排 Agent 提示词的第一版把派子 Agent 的理由写成了并列两条：
① 中间数据量大；② 子任务彼此独立。模型看到“两件事独立”就并行派了两个子 Agent ——
结果同一请求花了 **394.4s / ¥7.02**，比修正后慢 **11 倍**。

第②条是错的引导：**独立性只决定能不能并行，不决定要不要派子 Agent。**
主 Agent 自己的工具调用本来就能并行（见 7.8），而子 Agent 要重建一整套上下文、
自己跑完整的多轮推理。子 Agent 的真正价值是**上下文隔离**（中间数据不污染主上下文），
不是并行加速。

#### 降级链

无 LLM 时两种模式都走关键词意图 + 脚本化流程（`_run_scripted`），四条业务流仍可完整跑。

### 7.2 双档模型策略

| 档位 | 模型 | 承担任务 |
|---|---|---|
| 主模型 | `qwen3.8-max` | 根因分析、治理方案生成、容量核算（推理密集） |
| 快模型 | `qwen3.6-flash` | 上下文摘要、拓扑分析、数据采集汇报、无 LLM 降级时的兜底路由 |

Agent 定义里用 `model: primary` / `model: fast` 声明。**主模型连续失败达阈值后自动降级**到快模型（SSE `model_fallback`），保证可用性。

> 选型不是拍脑袋：探测端点列出 11 个可用模型后，逐个实测**文本生成 + 工具调用能力**
> （function calling，指模型能否按指定格式输出“该调哪个工具、传什么参数”），最终选出“支持工具且最快”的作为快模型。

### 7.3 多 Agent 分工与工具集划分

**为什么不用一个大 Agent**：22 个工具全塞给一个 Agent，工具选择准确率下降、提示词膨胀。先分诊再进专科，每个 Agent 只面对 **3~13 个工具**。

本质是**用工具集划分来压缩模型的决策空间** —— 工具越少，模型越不容易选错。就像医院先分诊再进专科，而不是让一个医生掌握全部科室的技能。

### 7.4 Skill 三层渐进式披露

**问题**：早期把整篇 Skill 拼进系统提示词，3 篇时尚可，扩到 8 篇后常驻成本超 5000 token，而大部分轮次用不到。

> **token（词元）**：大模型处理文字的最小单位，也是计费单位。中文大致 1 字 ≈ 1~2 token。
> 模型的输入窗口有上限（本项目按 200k token 标定），常驻内容越多，留给对话的空间越少、每轮花费也越高。

| 层 | 内容 | 加载时机 |
|---|---|---|
| **L1** | frontmatter：`name` / `description` / `when_to_use` | **常驻**系统提示词 |
| **L2** | `SKILL.md` 正文 | `load_skill(name)` 按需 |
| **L3** | `references/*.md` 深度细则 | `load_skill(name, reference=...)` 按需 |

**量化收益**：常驻 1009 字符 / 全量 23953 字符 = **常驻占比仅 4.2%**。

**一个刻意的偏离**：Agent 的**主 Skill 仍注入正文**，不只给 L1。因为 RiskAgent 的治理方法论是每轮都要用的核心知识，若要求它先调一次 `load_skill`，等于给每个治理请求多加一轮 LLM 往返。细节下沉到 L3 后主体已经很薄，这个折中代价很小。

### 7.5 上下文管理与三级压缩阶梯

#### 7.5.1 先理解问题：为何需要压缩

大模型一次能看的文字量有上限。而 Agent 排查故障时，每调一次工具都往上下文里塞一堆数据：

```
第 1 步：查指标   → 3000 字符的 JSON   ┐
第 2 步：查日志   → 8000 字符的日志   │ 全部堆在上下文里
第 3 步：查 trace → 5000 字符的 span   │ 越查越多
第 4 步：查慢日志 → 6000 字符         ┘
                                累计 22000+ 字符
```

**塞满了会发生什么**：API 直接报错（上下文超长），这一轮请求白费。所以必须在**塞满之前**主动腾地方。

#### 7.5.2 怎么判断「快满了」——压力（pressure）

```python
def pressure(self) -> float:
    by_chars  = self.total_chars() / config.CONTEXT_MAX_CHARS
    by_tokens = self.est_tokens()  / config.CONTEXT_MAX_TOKENS
    return max(by_chars, by_tokens)      # ← 取较大者
```

**为何两个口径取大值**：同样 24000 字符，全中文约 32000 token，全 JSON 只有 8000 token。

- 只看字符 → 中文会话压缩得太晚（已经爆 token 了字符数还没超）
- 只看 token → 对 JSON 过度保守（明明还能装很多却提前压缩）

取较大者 = 哪个先接近上限就听哪个的。

> token 估算系数**经真机实测校准**：CJK（中日韩汉字） 0.75 / 其余 0.5（实测 0.50 / 0.42，各留余量）。
> 旧系数（中文 1 token/字 + 其余 /4，再 ×4/3）的问题不是"保守"，而是**方向不一致**——
> 对中文高估 32%、**对 JSON 却低估 12%**，而低估恰恰是危险的那一侧
> （撞上限 → 整轮白费 → 还得紧急压缩重试）。

#### 7.5.3 三级阶梯：能省钱就别花钱

```
压力 ≤ 0.6（软阈值）  → 什么都不做
压力 > 0.6           → L1 微压缩（零 LLM 调用）
L1 之后压力仍 > 1.0  → L2 中段摘要（1 次快模型）
真的撞上「超长」报错 → L3 紧急压缩（force_compact）
```

**阈值经真机实测校准**（不是拍脑袋）：`CONTEXT_MAX_TOKENS=180000`、
`CONTEXT_MAX_CHARS=360000`。依据：flash 实测吃下 150,831 tokens；`est_tokens()`
校准后稳定高估约 1.2 倍，故 est 180k 对应真实约 150k，留 25% 给工具 schema
（~2k，**不计入** `est_tokens`）与模型输出。

**L1 微压缩：把大工具结果换成「取货单」**

从**最老的**工具结果开始，把超长的换成「结构感知预览 + 落盘指针」：

```
压缩前：tool 消息 = { 8000 字符的完整日志 JSON }
压缩后：tool 消息 = { 前 N 字符预览 + <persisted-output path="..." />
                        需要全文时调 read_tool_result }
```

数据没删，只是从「摊在桌上」变成「放进抽屉 + 贴标签」——**零成本且不丢信息**。

- **为何从最老的开始**：尾窗里的新结果是模型**当下正在用**的，动它会影响当前推理
- **何时停**：压到压力回落到软阈值以下就停（`if self.pressure() <= CONTEXT_SOFT_RATIO: break`）

**L2 中段摘要：请快模型写摘要**

L1 压完还超，说明是**轮次太多**而非单次结果太大，这时才动用 LLM：

```
压缩前： system │ 第1轮 │ 第2轮 │ ... │ 第8轮 │ 第9轮 │ 第10轮
               └────── 中段（被摘要） ─────┘   └── 尾窗保留 ──┘
压缩后： system │ [前序对话摘要] │ 第9轮 │ 第10轮
```

用**快模型**（摘要是轻结构化任务，不该占用主模型），提示词里明确要求「逐字保留关键数值、资源名、traceID、结论，**数值不得四舍五入或改写单位**」。

**★ 数值保真兜底（最关键的一环）**

上面那句提示词只是**请求**。模型做不到时没人知道——摘要里悄悄把 `P99 1.244s` 写成了「P99 约 1.2 秒」，后续所有结论就失去了精确依据。

所以压缩后做一次**机械对比**：

```python
lost = verifier.extract_numbers(source) - verifier.extract_numbers(digest)
if lost:
    picked = sorted(lost, key=lambda v: -abs(v))[:12]    # 大数优先，最多 12 个
    return f"\n[保真补录] 上文出现过但摘要未包含的数值：{shown}"
```

只补录**数值本身**、不重建上下文——目的是让模型知道「这些数存在过，别当它们不存在」，需要精确语境时可以用 `sql_query` / `read_tool_result` 复查。

> **踩过的坑**：第一版补录用 `f"{v:g}"` 格式化，把 `1162951` 写成了 `1.16295e+06`。结果：① 模型对不上工具返回里的原值；② 精度真的丢了（1.16295e6 = 1162950）。
> **用一个会改写数值的格式化函数做「保真」补录，等于自相矛盾。**

**L3 紧急压缩：撞墙之后的自愈**

前面都是**预防**。万一还是撞上了超长错误，`force_compact()` 无条件执行、尾窗更小（4 条），并对尾窗内大结果二次截断到 500 字符，然后**重试这一步**（前端收到 `compacted`）。

#### 7.5.4 一个必须小心的技术约束

OpenAI 兼容接口要求：**每条 `role="tool"` 必须紧跟在携带对应 `tool_call_id` 的 assistant 之后**。按「条数」粗暴切尾窗很容易切断这个配对：

```
0 system │ 1 user │ 2 A1(tool_calls=[a]) │ 3 tool(a)
4 A2(tool_calls=[b]) │ 5 tool(b) │ 6 A3(tool_calls=[c,d]) │ 7 tool(c) │ 8 tool(d)

messages[-6:] → 从索引 3 开始 → 尾窗以 tool(a) 开头
但 A1 已被压进摘要 → API 报 400
```

所以所有切片都走 `_safe_tail_start()`：从期望位置**向前扫**，只要落在 tool 消息上就继续前移，直到停在 assistant 或 user 上。

#### 7.5.5 不属于压缩的东西：scratchpad

```python
ctx.note("slow_sql", "SELECT * FROM orders WHERE ...")
ctx.note("p99_s", 1.244)
```

**scratchpad = 中间结论的便签**，与对话历史分开存，所以：压缩时不会被压掉、**续跑时刻意保留**（它是结构化中间结论，不是对话历史）、可跳 Agent 传递。

### 7.6 结论事实核对（幻觉治理）

#### 7.6.1 要解决什么问题

大模型会**编造看起来很真的东西**。运维场景里最典型的三种：

| 幻觉类型 | 例子 | 危害 |
|---|---|---|
| 编造标识符 | 「问题 trace 是 `a3f8b2c1d4e5f6a7`」（不存在） | 用户去查查不到，信任崩塌 |
| 记错资源名 | 实际是 `rds-mysql-order`，说成 `rds-mysql-orders` | **治理动作打到错误的实例上** |
| 编造数值 | 「P99 是 2.5s」（工具返回的是 1.244s） | 结论建立在假数据上 |

#### 7.6.2 核心设计：证据池的定义

```
证据池 = 模型【实际看到过】的全部文本
       ≠ 数据库里客观存在的所有数据
```

**这个边界划错了，整个机制就失效**。两个具体体现：

**① 只吸收预览，不吸收全文**

```python
def add_tool_result(self, tool_call_id, name, result, limit=None):
    preview = tool_results.persist_and_preview(...)   # 超长则落盘
    self.messages.append({"role": "tool", "content": preview})
    self.evidence.absorb(preview)      # ★ 只吸 preview，不是 result 全文
```

如果吸收全文：一个 8000 字符的结果落盘后模型只看到 2000 字符预览，但后 6000 字符里的数值也进了池子——模型说出那些数值时会被当成「有出处」，而它**根本没看到过**。

**② 模型自己写的文本不进池**

```python
def add_user(self, content, *, evidence: bool = True):
    ...
    if evidence:
        self.evidence.absorb(content)
```

续跑时的交接摘要、收口指令里的任务清单快照，都是**模型自己写的**。如果进池，模型编造的数字就被「洗白」成有出处的事实——**自己给自己作证**。所以这类注入一律 `evidence=False`。

#### 7.6.3 四类检查：分级而非一刀切

| 类别 | 检查什么 | 判定条件 | 处置 |
|---|---|---|---|
| **A1** | hex 十六进制标识符（trace_id） | 不在池中 | **报警 + 自纠正** |
| **A2** | 连字符资源名（`rds-mysql-order`） | 不在池中 **且** 与池中某项编辑距离 ≤ 2 | **报警 + 自纠正** |
| **B** | 关键数值 | 不在池中 | **只统计，不报警** |
| **C** | 证据的**时效** | 某份工具结果的数据最新时间远于当下（>30 分钟）且回答在描述“当前” | **自动重查最新数据复核**；数据源停更则降级为告警 |

**A1 为何可以硬报警**：`a3f8b2c1` 这种 hex 串**不可能被推算出来**。它要么是模型看到过的，要么就是编的，没有第三种可能。

**A2 为何要加「编辑距离 ≤ 2」**：只判「不在池中就报警」会误伤大量正常表述。加上距离条件后，只报**「近似但不相等」**：

```
说的：rds-mysql-orders   池里：rds-mysql-order   距离 1  → 报警 ✅（典型记错）
说的：payment-service    池里：rds-mysql-order   距离 大  → 不报（是另一个东西，不是笔误）
```

**★ B 为何刻意不报警（最能体现设计分寸的地方）**

模型做这些事时数值都**不在池中**，但它们全是**应该鼓励**的行为：

```
单位换算：工具返回 336500（微秒） → 模型说 336.5ms      ← 池里没有 336.5
聚合统计：工具返回 20 条记录      → 「共 20 条，平均 1.2s」 ← 平均值是算出来的
四则运算：39300m / 23400m         → 「超卖 167.9%」      ← 算出来的
```

**如果对这些硬报警，就是在惩罚模型正确地推理。** 误报会摧毁机制的可信度——用户看到满屏黄条警告，两天后就会忽略所有警告，包括真正的 A 类。所以 B 类只统计数量（`checked.numbers`）。

**★ C 类：从「只告警」升级为「自动重查复核」（时间维度，量化评测逆向驱动补上）**

A/B 类共同的盲区：**证据池是个无时间概念的集合**。一条两小时前的日志与一分钟前的日志没有任何区别。
量化评测里最严重的那次错误就落在这里（§3.1）：`query_logs` 无时间窗口且升序返回，拿回库里**最旧**的日志，
Agent 据此报出根因 —— 结论完全错，而**它引用的每一条日志都真实存在**，A/B 类一声不响。

C 类把时间戳**按工具结果逐份记录**（不汇成全局区间 —— 新旧数据混用时全局最大时间会被新数据掩盖），
并只在回答声称“当前/正在/目前”时才标 `time_risk`（历史回顾不算）。
**为何早期只告警**：数据陈旧是取数窗口的问题、不是模型措辞的问题，让它**重写**既多花一次往返也解决不了。

**为何后来改成自动重查**：那个判断没错，但结论下错了 —— 重写没用，**那就重新取数**。只挂一条「我的结论基于 31 分钟前的数据」、然后等用户自己想到追问「用最新数据再确认一次」，等于把系统该做的事推给用户，而用户很可能压根没注意到那条警示。

现在的处置：检测到 C 类即**自动带工具重查过期数据源**，并要求逐项比对新旧结论 —— 变了要写「初判 X → 复核后 Y」，没变也要明说「已用最新数据复核，结论不变」（否则用户无法区分「确认过没变」和「没去确认」）。三道护栏：复核次数上限（数据源停更时不至于死循环）、复核步数上限、中断与预算检查；若重查后数据**仍然**陈旧（典型如采集器挂了），如实降级为告警，不因「尝试过」就闷掉。
这个机制在后续评测里真机生效：揪出 `sql_query` 无时间约束的同类缺口（“数据最新只到 56 分钟前而结论在说当前”）。

#### 7.6.4 「什么算关键数值」的口径

```python
def _is_informative(v: float) -> bool:
    if v != int(v):
        return True              # ★ 有小数部分的一律算
    return abs(v) >= 11          # 纯整数要求 ≥ 11
```

- **为何有小数就算**：本项目最关键的度量值恰恰是小数——P99 `1.244s`、错误率 `1.78%`、`request_time 0.333`。
  > 第一版用「结对值 ≥ 11」一刀切，把这些**全滤掉了**——等于漏掉了最该核对的一类。这个缺陷是后来写压缩用例时才暴露的。
- **为何整数要 ≥ 11**：小整数几乎必然出现（序号、条数、副本数、规则编号里的数字），拿它们核对只会稀释信号。

#### 7.6.5 数值匹配的三重容错

模型说的数和池里的数**字面不同但其实是一回事**，这些都要认：单位换算（毫核↔核、秒↔毫秒）、四舍五入（`1.244` ↔ `1.24` ↔ `1.2`）、**中文量级约等**。

量级约等只对**万/亿**启用，且要求**相对误差 < 1%**：

```
116 万 → 1160000 vs 1162951，误差 0.25% → 命中 ✅
117 万 → 1170000 vs 1162951，误差 0.6%  → 命中 ✅
118 万 → 1180000 vs 1162951，误差 1.5%  → 不命中
200 万 → 2000000 vs 1162951，误差 72%   → 不命中
```

**容差刻意收窄到 1%**：放开就会让任意两个数互相「匹配」，命中率这个指标就变成没有意义的数字了。

#### 7.6.6 效果与前端呈现

- 真机多场景评估：**A 类零误报**，核对量 90 个数值全部命中；C 类在真机抛障评测中报对（揭出旧数据当当前）
- 跨段不丢：续跑时证据池保留（它只存指纹，与上下文体量无关）
- 触发时前端在回答上方显示黄条（`verify_warning`），列出可疑标识符与「说的 vs 最接近的真实项」

### 7.7 三态权限门禁与审计

#### 7.7.1 要解决什么问题：Agent 能改生产环境，这很危险

这个 Agent 手里有这些工具：

```
patch_deployment      改 Deployment 配置（副本数、探针、资源配额）
create_db_index       在生产库上建索引
upgrade_rds_instance  给 RDS 升配（花钱！）
create_pdb            创建 PodDisruptionBudget
ingest_data           清库重灌数据
```

如果模型判断错了，这些动作会**直接作用在真实环境上**。比如它误判「order-service 副本太多」，把 3 副本缩成 1——线上直接出事。所以需要一道门禁：**危险动作必须有人点头**。

#### 7.7.2 三态模式分别用在什么场景

| 模式 | 场景 | 行为 |
|---|---|---|
| **`readonly`** | **日常巡检**、给领导演示、只分析不动手 | 只允许只读 + 写本平台业务表；治理动作与配置变更**直接拒绝** |
| **`confirm`**（默认） | **正常使用**——人在电脑前 | 危险操作**弹卡片阻塞等待**用户确认 |
| **`auto`** | **无人值守**（如凌晨定时巡检自动修低危问题） | 白名单内自动放行，破坏性仍需人工 |

**readonly 的一个重要细节**：它不是「什么都不让写」，而是**允许写本平台自己的业务表**：

```python
if mode == "readonly":
    if spec.writes_business_data and not spec.is_destructive:
        return Decision("allow", REASON_MODE, "只读巡检模式允许写入本平台业务表")
    return Decision("deny", ...)
```

**为何**：`run_risk_scan`（跑扫描）与 `build_topology`（建拓扑）需要把结果写进 `risk_findings` / `topology_edges`。如果连这个都禁，只读模式下就**没法跑扫描了**——而巡检恰恰是只读模式最主要的用途。边界划在「**改的是我们自己的记录表，还是外部真实环境**」。

#### 7.7.3 四层门禁，逐层判定

```python
def decide(tool_name, args, mode="confirm", session_approvals=frozenset()):
    spec = registry.get_spec(tool_name)

    # ① 未知工具 → deny（模型幻觉出一个不存在的工具名）
    if spec is None:
        return Decision("deny", REASON_RULE, f"未知工具 {tool_name}")

    # ② 只读工具 → 任何模式都放行
    if spec.is_read_only:
        return Decision("allow", REASON_RULE)

    # ③ 运行模式 → readonly 拦治理动作
    if mode == "readonly": ...

    # ④ 工具自身逻辑 → 默认 ask（fail-closed）
    behavior = "ask"
    if spec.check_permissions:
        try:
            behavior = spec.check_permissions(args or {})
        except Exception:
            behavior = "ask"        # 判定函数自己抛异常 → 按需确认处理
```

注意第 ④ 层的 **fail-closed** 思路：默认值是 `ask`（要确认）而非 `allow`，连「判定函数自己抛异常」都归到 `ask`。**不确定时选择更安全的那条路。**

#### 7.7.4 ★ auto 模式用白名单而非黑名单

这是整个门禁最重要的设计决策。

```python
# ❌ 黑名单思路：只要不是 is_destructive 就放行
if mode == "auto" and not spec.is_destructive:
    return allow

# ✅ 白名单思路：只有明确标记「只写本平台业务表」的才放行
if mode == "auto" and spec.writes_business_data and not spec.is_destructive:
    return allow
```

**为何必须是白名单**，两个理由：

1. **配置变更类工具虽非破坏性，但影响面更大**。`create_risk_rule`（新建告警规则）不破坏任何数据，但它会**改变后续所有扫描的行为**——影响面远大于一次性数据写入。
2. **对未来新增工具 fail-closed**（更关键）。黑名单逻辑下，只要有人新加工具时**忘标** `is_destructive`，auto 模式就会自动放行它。白名单则相反——忘标的工具默认需要确认。

> 一句话：**黑名单的漏洞会随时间增长，白名单的不便是恒定的。**

#### 7.7.5 会话内批准的粒度

用户劾「本次会话都允许」时，记住的 key 是**工具 + 主要目标资源**：

```python
def approval_key(tool_name, args):
    target = (args.get("name") or args.get("app") or args.get("instance_id")
              or args.get("table") or args.get("rule_id") or "*")
    return f"{tool_name}:{target}"
```

效果：同一个资源不再反复弹窗，但**换了资源仍会重新询问**——不会一次授权就放开全部。

#### 7.7.6 审计：回答「这条变更是谁批准的」

每个决策都带 `reason_type`，写入 `agent_audit` 表：

| reason_type | 含义 |
|---|---|
| `rule` | 工具固有属性决定（未知工具 / 只读） |
| `mode` | 运行模式决定 |
| `tool` | 工具自身的 `check_permissions` 决定 |
| `user` | 用户在会话内已批准 |
| `auto_approve` | **历史值**，逃生阀已移除，保留仅为解读旧记录 |

> 一个安全决策：曾有个 `PERMISSION_AUTO_APPROVE` 环境变量逃生阀，前端确认卡片上线后**被彻底删除**——因为留着它就是一个危险的后门。

工具的安全标签（`ToolSpec`）：`is_read_only` / `is_destructive` / `writes_business_data` / `check_permissions` / `audit_repr` / `concurrency_safe`。

### 7.8 并行子 Agent

这部分有两个不同层次的「并行」，容易混淆，先分清：

```
层次一：工具并行   —— 一轮里模型同时要调 3 个只读工具 → 并发执行
层次二：子 Agent 并行 —— 模型同时派 2 个子 Agent → 因为 dispatch_agent 本身是只读工具，
                        所以走的是【同一套工具并行机制】
```

也就是说：**子 Agent 的并行，本质上就是工具并行的一个特例**。

#### 7.8.1 何时会调用子 Agent

模型自己决定，通过调 `dispatch_agent` 工具。系统提示词与 Agent 定义里给了明确指引：

**OpsAgent 的定义里写着**：
> 「遇到需要深度分析且中间数据量大的请求（全量日志分析、多轮 trace 下钻），派对应的专家子 Agent 而不是自己硬做 —— **子 Agent 的中间数据不会污染本轮上下文**。」

**DiagnoseAgent 的定义里写着**：
> 「多条独立假设可以**并行**派子 Agent 分别验证，再综合它们的证据。」

所以两个典型触发场景：

| 场景 | 为什么派子 Agent |
|---|---|
| **中间数据量大** | 子 Agent 有独立上下文，它翻 100 条日志的过程不会挤占主上下文，只回传结论 |
| **多条独立假设** | 可以并行验证，省时间 |

#### 7.8.2 何时并行、何时串行——判定规则

这是本节最核心的问题。判定发生在 `_partition()`：

```python
def _partition(tool_calls) -> list:
    batches, cur = [], []
    for tc in tool_calls:
        spec = registry.get_spec(tc.function.name)
        # ★ 必须【同时】满足：只读 + 标记为并发安全
        parallelizable = bool(spec and spec.concurrency_safe and spec.is_read_only)
        if parallelizable:
            cur.append(tc)          # 攒进当前批
            continue
        if cur:
            batches.append(cur)     # 遇到不可并行的 → 先把前面的批封口
            cur = []
        batches.append([tc])        # 它自己单独一批
    if cur:
        batches.append(cur)
    return batches
```

**两个条件必须同时满足**：
- `is_read_only` —— 保证无副作用
- `concurrency_safe` —— 保证作者**确认过**它并发安全（不共享可变状态等）

**只有连续的可并行工具才合成一批**。举例：

```
模型这一轮要调：[查指标, 查日志, 扩副本, 查拓扑]

分批结果：      [[查指标, 查日志],  [扩副本],  [查拓扑]]
                 └─ 并发执行 ─┘    └串行┘    └单个┘
```

**为什么必须这样切**：保证「**写操作之前的读都已完成、写操作之后的读看到的是写之后的状态**」——顺序语义不被打乱。如果把「查拓扑」也并到第一批，它可能在「扩副本」之前就跑完了，读到的是旧状态。

#### 7.8.3 并行具体怎么执行

```python
def _execute_batch(batch, ctx, run, agent_name):
    if len(batch) == 1:
        yield from _execute_one(batch[0], ...)      # 单个就别开线程池了
        return

    workers = min(len(batch), config.MAX_PARALLEL_TOOLS)   # 并发度上限

    def work(tc):
        # ★ 每个 worker 独立收集写操作与事件，【绝不触碰共享的 ctx】
        deferred = _Deferred()
        events = list(_execute_one(tc, ctx, run, agent_name, deferred=deferred))
        return deferred, events

    with ThreadPoolExecutor(max_workers=workers, thread_name_prefix="tool") as ex:
        results = list(ex.map(work, batch))   # map 保证【按输入顺序】返回

    for deferred, events in results:
        deferred.flush()          # ★ 串行写上下文与审计，顺序与 tool_calls 一致
        yield from events
```

三个关键点：

**① `_Deferred` 延后写入**：worker 线程里**不直接改** `ctx`（那是共享状态，并发改会乱）。而是把「要写什么」记在自己的 `_Deferred` 里，等回到主线程再按原顺序 `flush()`。

**② 保序**：`ThreadPoolExecutor.map` 保证按输入顺序返回结果。所以虽然执行是乱序完成的，**写入上下文和产出事件的顺序仍与模型请求的顺序一致**——模型看到的世界是有序的。

**③ 事件旁路**：子 Agent 的事件走 `push_event` 而非 yield。因为它们产生在 worker 线程里，主 generator 阻塞在 `ex.map()` 上，**跨线程无法 yield**。这是「能 yield 就走主通道」这条准则的**唯一例外**。

#### 7.8.4 实测数据

| 指标 | 结果 |
|---|---|
| 是否真并发 | ✅ 峰值并发 2，总耗时 **0.61s**（串行需 1.2s） |
| 并发度约束 | ✅ 6 个子 Agent 时峰值压在 4（`MAX_PARALLEL_TOOLS`） |
| 真机验证 | 两个 `dispatch_agent` 的时间戳相隔 0.1s |

#### 7.8.5 ★ 预算语义：独立上限 + 向上归集

这是子 Agent 机制里最精妙的设计。

```
子 Agent 的预算【上限】是独立的     → 防止单个子 Agent 跑飞
子 Agent 的预算【消耗】归集到父     → 保证整轮总开销封顶
```

```python
# dispatch_agent 末尾
_run.add_usage(prompt_tokens=sub_run.tokens_in,
               completion_tokens=sub_run.tokens_out)   # ★ 归集到父
```

**为什么两者都要**：
- 只有独立上限 → 派 5 个子 Agent 就能烧 5 倍预算，用户设的上限形同虚设
- 只有共享预算 → 一个子 Agent 就能把整轮预算吃光，其他任务没得做

> 代码注释里写得很直白：**「独立预算」指的是独立的【上限】，不是免费。**
>
> 这个缺陷是真机实测才发现的——单测覆盖不到，因为它是**语义**错误而非逻辑错误。

> **当前策略：预算熔断已停用**（`RUN_MAX_TOKENS` / `SUBAGENT_MAX_TOKENS` 都是 0，
> `<= 0` 表示不限制），目标是让 Agent 跑到任务完成。但**归集逻辑照旧**——
> 它同时决定了用量与花费显示得准不准，与要不要熔断是两件事。
> 用量统计与 `est_cost_cny` 花费估算继续每步上报；无上限时 `budget_pct` 为 `None`，
> 前端据此不显示"预算 x%"（填 0 会显示成"预算 0%"，那是在骗人）。

#### 7.8.6 子 Agent 失败/超预算时的处理

**问题**：原来子 Agent 超预算就直接返回，父只拿到一句「`[子 Agent aborted] 超出 token 预算`」——什么都用不上，于是**倾向于原样重派一次**。真机白烧过 40435 token。

**两个修复**：

**① 带回部分结论**（零 LLM 调用）

```python
def _abort_events(reason, last_thinking, ctx):
    partial = _partial_conclusion(last_thinking, ctx, reason)
    if partial:
        yield {"type": "answer", "text": partial, "partial": True, ...}
    yield {"type": "aborted", "reason": reason}
```

用已积累的 `last_thinking` + `scratchpad` 拼一份标注为「不是完整结论」的部分结论。

**为什么不调 LLM 重新总结**：触发原因往往就是**预算已耗尽**，再花一次往返自相矛盾。而这些信息是**已经产生并付过费**的——真正的缺陷是把它们丢了，不是没去生成新的。

**② 劝阻重试**

```python
if status != "ok":
    out["retry"] = False
    out["hint"] = "...**不要用相同任务再派一次**..."
```

同样的输入不会有不同的结果，而消耗已经归集到父了。

### 7.9 任务清单与分段续跑

#### 7.9.1 要解决什么问题

Agent 干活有个步数上限（`MAX_AGENT_STEPS`），防止它无限循环。但复杂任务（比如「全面体检 + 生成治理方案 + 执行 + 复扫」）可能真的需要很多步。

**步数用完了怎么办**？两个糟糕的选择：
- 直接停 → 用户拿到一个半成品，还得重新问一遍
- 把上限调到很大 → 失去了防跑飞的保护

**解法**：把 `MAX_AGENT_STEPS` 重新定义为**单段**上限，允许在满足条件时「开新的一段」继续跑。

#### 7.9.2 任务清单：让「还没做完」变成结构化信号

模型用 `update_plan` 工具维护一份清单：

```json
[
  {"title": "采集最新数据",     "status": "done"},
  {"title": "跑风险扫描",       "status": "done"},
  {"title": "定位 DB-002 根因", "status": "in_progress"},
  {"title": "生成治理方案",     "status": "pending"}
]
```

前端收到 `plan_update` 事件后渲染成清单，用户能实时看到进度。

> 真机验证时模型的**第一个动作**就是 `update_plan`——说明这个工具的描述写得足够清楚，模型知道该先规划。

#### 7.9.3 ★ 续跑的三道闸门（顺序有意义）

```python
def can_continue(self) -> Tuple[bool, str]:
    # 闸门 1：预算优先 —— 超预算/被中断时绝不续跑
    # 闸门 2：续跑次数上限（RUN_MAX_CONTINUATIONS）
    # 闸门 3：必须有【结构化的未完成信号】—— plan 里有非 done 的步骤
```

逐条解释：

**闸门 1：预算优先**。这是**最高优先级**。如果是因为超预算或用户中断而停下的，绝不续跑——否则「预算上限」这个概念就没意义了。

**闸门 2：次数上限**。防止「续跑 → 又用完 → 再续跑」无限循环。

**闸门 3：结构化的未完成信号**。必须清单里**真的**有非 `done` 的步骤才续跑。

> 这条闸门的设计很关键：**没维护清单时不猜、也不问模型「你做完了吗」**，直接交回用户决定。
>
> 为什么不问模型：模型倾向于说「还没完，我再查查」——这会导致无意义的续跑。**不能让被约束的对象自己决定约束是否解除。**

#### 7.9.4 ★ 关键不变量：续跑只重置步数，绝不重置预算

```
新的一段：步数计数器 → 归零 ✅
          token 预算  → 继续累计，绝不归零 ❌
```

如果预算也重置，那么「最多花 X token」这个承诺就是假的。真机验证时专门确认了这一点。

#### 7.9.5 交接摘要（handoff）vs 收尾总结（wrap_up）

这是两个**容易混淆但完全不同**的东西：

| | handoff（交接摘要） | wrap_up（收尾总结） |
|---|---|---|
| **读者** | 下一段的**自己** | **用户** |
| **内容** | 已确认的事实、下一步该干什么 | 结论、建议 |
| **失败处置** | 生成失败 → 不能续跑（没有交接单等于失忆） | 生成失败 → 退化成把已有信息给用户 |

续跑时上下文重置成「system + 一条交接摘要」：

```python
def reset_for_continuation(self, handoff: str) -> int:
    self.messages = [
        self.messages[0],                                    # system
        {"role": "user", "content": f"[上一段执行的交接摘要，请据此继续]\n{handoff}"},
    ]
    # scratchpad 刻意保留（结构化中间结论，不是对话历史）
    # evidence 同样保留（只存指纹，与体量无关）
```

**为什么这里可以放心丢掉全部历史**（而 `compact` 要小心处理 `_safe_tail_start`）：因为步数耗尽是一个**天然的分段点**，此刻模型刚被要求写完交接单，不用担心截断在半个 tool_call 上。

真机实测跑出过 **3 段**。

### 7.10 可中断、自愈与降级

这三个是不同的东西，分开讲。

#### 7.10.1 可中断：用户点「停止」要能真停下

**难点**：Agent 正在跑的时候，可能卡在 LLM 请求里、或在执行工具。不能强杀（会留下不一致状态）。

用的是**协作式中断**——在三个检查点主动查「是否被要求停止」：

```
检查点 ①：每步开头        stop, why = run.should_stop()
检查点 ②：LLM 调用中      except llm.Aborted
检查点 ③：工具批执行前    if run.abort.is_set()
```

`should_stop()` 实际上检查三件事：

```python
def should_stop(self):
    if self.abort.is_set():
        return True, "用户中断"
    if self.tokens_in + self.tokens_out > self.max_tokens:
        return True, f"超出 token 预算（... / ...）"
    if time.time() - self.started_at > self.max_wall_s:
        return True, f"超出时间预算（...s / ...s）"
    return False, ""
```

所以「中断」和「超预算」走的是**同一条路**，处置也一样：带回部分结论再退出。

#### ★ 中断时必须补齐 tool_result

```python
if run.abort.is_set():
    # 必须补齐【剩余全部】tool_call 的结果，否则下一轮 API 400
    _fill_remaining(ctx, msg.tool_calls[done:], "用户中断，工具未执行")
```

**为什么**：模型说「我要调 A、B、C 三个工具」，如果只执行了 A 就中断，上下文里就有 3 个 tool_call 但只有 1 个 tool_result。下一轮请求 API 直接报 400。

所以即使是「没执行」，也要写一条「因中断未执行」的结果占位。这是 `_execute_one` 的**铁律**：每一条提前 return 的路径都必须先写 tool_result。

#### 7.10.2 自愈：错误不等于失败，先试着自己解决

| 遇到什么 | 怎么自愈 | 前端事件 |
|---|---|---|
| **主模型连续失败** | 降级到快模型再试（**只降一次**） | `model_fallback` |
| **上下文超长错误** | `force_compact()` 紧急压缩后**重试这一步** | `compacted` |

注意「只降一次」——如果快模型也失败，就是真的失败了，不再无限重试。

#### 7.10.3 降级：外部依赖没了也要能用

这是两道**保底防线**，让项目在断网/无权限环境下仍可演示：

| 依赖挂了 | 降级方案 | 影响 |
|---|---|---|
| **未配 API Key / LLM 不可用** | 意图识别 → 关键词正则；执行 → 脚本化流程（`_run_scripted`） | 四条业务流仍可完整跑，只是不智能 |
| **数据库连不上** | 自动降级本地 SQLite（`backend/aiops.db`） | 表结构与代码完全一致，功能不变 |

**关键词降级的实现**：

```python
_KEYWORD_RULES = [
    ("full_checkup",   r"全面体检|一条龙|全流程|完整巡检"),
    ("data_ingest",    r"采集|同步数据|导入数据|拉取数据|入库"),
    ("topology",       r"拓扑|链路梳理|调用关系|依赖关系"),
    ("risk_scan",      r"风险|扫描|巡检|隐患|体检"),
    ("fault_diagnose", r"故障|很慢|超时|报错|错误率|定位|根因|排查|异常|挂了|不可用"),
    ...
]
```

顺序有讲究——`full_checkup` 在最前面，因为「全面体检」同时含「体检」（会命中 risk_scan），必须先匹配更具体的。

## 8. 资产清单

### 8.1 八个专职 Agent 都是干什么的

#### 8.1.1 先理解为什么要分多个

**如果只有一个 Agent**，它得面对全部 22 个工具。后果：
- 工具选择准确率下降（选项太多）
- 提示词膨胀（22 个工具的描述都要塞进去）

分工后分两层：顶层一个**编排 Agent**面向用户，它自己拿不下的重活才派给下面的专科 Agent；
每个专科 Agent 只面对 **3~13 个工具**。本质是**用工具集划分来压缩模型的决策空间** —— 和「先分诊、再进专科」一样。

#### 8.1.2 八个 Agent 一览（大白话版）

| Agent | 大白话职责 | 用哪档模型 | 工具数 | 能被派发 |
|---|---|---|---|---|
| **OrchestratorAgent** | **总台调度者**（model 默认下的入口）。持全部工具，自己决定自己干还是派专科 | 主 | 21 | — |
| **OpsAgent** | **前台/全科医生**（intent 模式下的入口）。回答日常问题，搞不定就叫专家 | 主 | 13 | — |
| **DataAgent** | **数据搬运工**。把监控数据拉进库，汇报搬了多少 | 快 | 3 | — |
| **TopologyAgent** | **画关系图的**。从调用链看出谁依赖谁，哪条链有问题 | 快 | 4 | ✅ |
| **RiskAgent** | **体检医生 + 执刀的**。扫风险、开方案、动手治、复查 | 主 | 12 | ✅ |
| **DiagnoseAgent** | **急诊科**。「接口很慢」这类现场问题，按五步法找根因 | 主 | 9 | ✅ |
| **CapacityAgent** | **算账的**。CPU/内存超卖多少、该缩多少 | 主 | 5 | ✅ |
| **DBOpsAgent** | **DBA**。慢查询、索引怎么建、连接数水位 | 主 | 5 | ✅ |

> 为什么同时有 OrchestratorAgent 与 OpsAgent：前者是默认（model）调度下的顶层入口，
> 后者是旧（intent）调度下“数据查询/日常问答”意图对应的 Agent。两种调度共用同一批专科 Agent。

#### 8.1.3 逐个说清楚

#### OrchestratorAgent — 总台调度者（默认入口）
**什么时候是它**：model 默认调度下，所有用户请求都先到它。

**它的特点**：持有全部工具（21 个）+ 派发能力 + 治理工具，**自己决定要不要派专科 Agent、派几个、串行还是并行**（不再由代码写死的意图表决定）。

**它的定义里有一条关键引导**：
> “默认自己做。派子 Agent 的唯一理由是这个子任务的中间数据多到会挤爆上下文——
> “两件事独立”不是派子 Agent 的理由（自己的工具调用本来就能并行）。”
这条引导是踩坑后加的（见 7.1）：早期有一版把“独立”当成派子 Agent 的理由，导致同一请求慢了 11 倍。

#### OpsAgent（general）— 前台
**什么时候是它**：仅在旧（intent）调度下作为入口——数据查询、指标解读、日常运维问答。

**它的特点**：工具 13 个，同样可以派专家子 Agent。model 默认上线后，它的入口角色被 OrchestratorAgent 接替。

#### DataAgent — 数据搬运工
**什么时候是它**：「采集集群可观测数据」这类请求。

**用快模型**——搬数据不需要复杂推理。

**它的定义里有两条很有意思的约束**：
> 「采集完成后必须汇报**每张表的入库行数与时间覆盖范围**，而不是只说'采集成功'。」
>
> 「行数为 0 的表要单独点出来 —— 那通常意味着该类事件在窗口内**没有发生**（如 k8s_events），而**不是采集失败**，需要说清区别以免误判。」

第二条尤其重要：不加这条，模型看到 0 行会说「采集失败」，误导用户。

#### TopologyAgent — 画关系图的
**什么时候是它**：「梳理服务拓扑」「看看调用关系」。

**做什么**：从 trace span 数据反推出服务依赖图，并识别**病灶边**（哪条调用链的错误率/延迟异常）。

**它的定义约束**：
> 「输出必须点明**哪几条边异常、异常在哪个指标上**（错误率还是延迟），而不是罗列全部边。没有异常边时要明确说'未发现异常边'，不要含糊。」

#### RiskAgent — 体检医生兼执刀者
**什么时候是它**：风险扫描、制定/执行治理计划、生成告警规则、验证闭环。

**工具最多的写操作者**（12 个工具里含 4 个破坏性工具：`patch_deployment` / `create_pdb` / `create_db_index` / `upgrade_rds_instance`）。

**它是唯一能真正改变环境的 Agent**——所以权限门禁主要就是在管它。

#### DiagnoseAgent — 急诊科
**什么时候是它**：用户报告「接口慢/报错/超时」，或要定位某条风险的根因。

**核心方法论**（写在 `fault_diagnosis` Skill 里的五步排查法）：

```
① 确认现象  → ② 定位层级 → ③ 深挖数据 → ④ 排除干扰 → ⑤ 输出根因链
```

**两条硬约束**：
> 「每一步结论都必须有工具返回的**真实数值**支撑，禁止推断。」
>
> 「多条独立假设可以**并行派子 Agent**分别验证，再综合它们的证据。」

它是**并行子 Agent 的主要使用者**。

#### CapacityAgent — 算账的
**什么时候是它**：核算命名空间超卖率、分析资源配额缺失、计算 CPU limit 下调幅度。

**专精容量域**（CAP-001~004）。定义里要求**先取 `capacity_rules` 细则**再动手。

**一个省钱的技巧写进了定义**：
> 「核算超卖率时优先用 finding 的 evidence 字段（`sum_pod_cpu_limit_m` / `sum_node_allocatable_m`），能省掉多次 k8s_resources 查询。」

#### DBOpsAgent — DBA
**什么时候是它**：分析慢查询、设计索引、诊断 RDS 连接或内存水位。

**专精数据库域**（DB-001/002 与 CAP-004）。

**两条专业约束**：
> 「慢查询分析必须给出 `rows_examined / rows_sent` 比值 —— 它比绝对值更能说明索引缺失。」
>
> 「索引列序要从实际 SQL 的 WHERE / ORDER BY 推导，不要套用固定组合。」

#### 8.1.4 「可派发」是什么意思

5 个标了 `dispatchable: true` 的 Agent 可以被顶层 Agent 通过 `dispatch_agent` 工具调用（作为子 Agent）。

`OrchestratorAgent` / `OpsAgent` / `DataAgent` **不可派发**：
- 前两个是**入口**（分别对应 model / intent 调度），派它们等于绕圈
- DataAgent 的采集是**写操作**，不适合放进只读的子 Agent 通道

> 这里踩过一个坑：`SUBAGENT_TYPES` 曾**硬编码**成一个列表，漏了 capacity 和 dbops——导致这两个专家**静默失效**（模型想派也派不到）。现在改成从 Agent 定义动态生成 `dispatchable_keys()`，并有常驻测试盯着。

### 8.3 十三类风险规则

五个域：**HA**（高可用）、**CAP**（容量）、**DB**（数据库）、**API**（接口性能）、**CACHE**（缓存）。

#### 8.3.1 HA 域：高可用配置缺陷（4 条）

| 规则 | 级别 | 判定 | 为什么是风险 |
|---|---|---|---|
| `HA-001` | P1 | 多副本 Deployment **单可用区**部署 | 该可用区故障 → 服务整体挂掉，多副本白配 |
| `HA-002` | P1 | Deployment **单副本**运行 | 这个 Pod 挂了就没了，无冗余 |
| `HA-003` | P2 | 缺失**存活/就绪探针** | K8s 不知道容器是否健康，挂了不重启、没就绪就接流量 |
| `HA-004` | P2 | 缺失 **PodDisruptionBudget** | 节点维护时 K8s 可能一次驱逐全部副本 |

#### 8.3.2 CAP 域：容量与配额（4 条）

| 规则 | 级别 | 判定 | 为什么是风险 |
|---|---|---|---|
| `CAP-001` | P1 | 缺失 **CPU request** | 调度器无法正确安排，容易挤在一台机器上 |
| `CAP-002` | P2 | 缺失**内存 limit** | 内存泄漏时会吃掉整个节点，拖垮邻居 |
| `CAP-003` | P1 | 命名空间 **CPU 超卖率 > 150%** | 所有 Pod 同时满载时资源不够，互相抢 |
| `CAP-004` | P2 | RDS **内存使用率 > 85%** | 接近上限，缓冲池不足会导致性能劣化 |

#### ★ CAP-003 的治理顺序陷阱

这条规则有个**反直觉**的性质，实测数据说明问题：

```
初始状态：             超卖率 167.95%
把 order-service 扩到 3 副本后： 超卖率 202.14%   ← 反而升高了 34.2 个百分点！
```

**原因**：扩副本会**增加** CPU limit 总和，而节点可分配量不变 → 超卖率上升。

**所以治理顺序必须是**：先做其他修复（扩副本、补探针等），**CAP-003 最后处理**。这条经验写进了 `risk_governance` Skill，并给出了下调幅度的反算算法（用 `evidence.sum_pod_cpu_limit_m` 与 `evidence.sum_node_allocatable_m` 计算目标值）。

#### 8.3.3 DB 域：数据库（2 条）

| 规则 | 级别 | 判定 | 为什么是风险 |
|---|---|---|---|
| `DB-001` | P1 | RDS **连接使用率 > 80%** | 连接耗尽 → 新请求直接失败 |
| `DB-002` | P2 | **无索引慢查询**（全表扫描） | 拖慢数据库，连带影响所有使用者 |

`DB-002` 的判定依据是 `rows_examined / rows_sent` 比值——实测数据里扫了 **1162951 行**只返回 **20 行**，比值 5.8 万倍，典型的缺索引。

#### 8.3.4 API 域：接口性能（1 条）

| 规则 | 级别 | 判定 |
|---|---|---|
| `API-001` | P1 | 接口 **P99 > 1s** 或**错误率 > 1%** |

#### 8.3.5 CACHE 域：缓存（2 条）

| 规则 | 级别 | 判定 | 为什么是风险 |
|---|---|---|---|
| `CACHE-001` | P1 | 缓存实例 **内存使用率 > 80%** | 接近 maxmemory 会成批驱逐 key，命中率塔式下跌、请求全量击穿到数据库 |
| `CACHE-002` | P1 | 缓存实例 **CPU 使用率 > 70%** | Redis 命令执行是单线程的，70% 已接近拐点，主线程排队后所有命令 RT 齐涨 |

两条阈值都比对应的 RDS 规则更保守（内存 80% vs CAP-004 的 85%），因为缓存是多服务共享依赖，
一处失效会同时放大成多条链路的故障。实测缓存雪崩场景下两条必然同时命中（内存 41.9%→86.8%、CPU 17.9%→77.5%）。

#### ★ 这两条是怎么来的：规则体系本身的边界

它们是**量化评测逆向驱动补上的**。Redis 缓存雪崩场景第一次跑评测时，当时的 11 条规则
里没有任何一条涉及缓存层，规则侧只报出了下游的 API-001（接口变慢）——
根因完全报不出来，实例定位 0%。

但补两条规则**并不能解决“规则有限”这件事本身**：消息队列积压、连接池耗尽、
外部依赖限流、客户端重试风暴、证书过期……仍然一条规则都没有。任何预先写死的
规则集都只能覆盖“有人想到过并且愿意写下来”的那部分问题。

所以真正的兜底做在 **Agent 侧而不是规则侧**，分三层写进提示词与 Skill：

| 层次 | 内容 | 位置 |
|---|---|---|
| 工作准则 | “规则没报不等于正常”、排查范围不受风险报告限制 | `agents/base.py` 准则 9 |
| 方法论 | 无规则覆盖时的通用三步：水位对比 / 时间对齐 / 拓扑位置 | `risk_governance` Skill「规则之外」一节 |
| 沉淀 | 发现新模式后用 `create_risk_rule` 变成下次自动判定 | 同上 |

反向约束也写了：**规则命中也不等于它就是根因**。API-001 大多数时候是别人的症状
（慢查询、缓存失效、下游超时），直接拿它当结论会把真正的根因放过。

#### 8.3.6 live 模式的判定语义

| | static 模式 | live 模式 |
|---|---|---|
| 时间范围 | 全表聚合 | **5 分钟滑动窗口** |
| 分组 | 整体 | **按实例分组** |

**按实例分组为什么关键**：环境里有两台 RDS。如果全表聚合，一台出问题会导致**两台都告警**。分组后 `resource_ref` 精确到 `rds-mysql-order`，另一台不误报。

同时还做了**低流量防抖**——请求量太少的接口不参与 API-001 判定，避免 1 个请求恰好慢就报 P99 异常。

### 8.4 十七张数据表

#### 8.4.1 可观测数据（8 张，采集入库）

| 表 | 存什么 | 对应数据源 |
|---|---|---|
| `metrics` | 时序指标（历史） | 云监控 CMS |
| `realtime_metrics` | 实时指标（10s 一次的水位/容量/带宽） | CMS 实时通道 |
| `ingress_logs` | 网关访问日志（含 request_time、status） | 日志服务 SLS |
| `app_logs` | 应用日志 | SLS |
| `slow_logs` | RDS 慢查询日志（含 rows_examined） | SLS |
| `trace_spans` | 链路追踪 span | Trace |
| `k8s_resources` | K8s 资源配置快照（Deployment/Pod/Node） | K8s API |
| `k8s_events` | K8s 事件 | K8s API |

> `metrics` 与 `realtime_metrics` 分开的原因：采集频率与保留策略不同（定时 60s vs 实时 10s），混在一张表会让滑窗查询变慢。

#### 8.4.2 拓扑（1 张）

| 表 | 存什么 |
|---|---|
| `topology_edges` | 服务依赖边（含错误率、延迟等边上指标，用于标红病灶边） |

#### 8.4.3 风险与治理（5 张）

| 表 | 存什么 |
|---|---|
| `risk_rules` | 规则定义（11 条内置 + AI 生成的） |
| `risk_findings` | 扫出来的具体风险（含 `evidence` JSON、`resource_ref`、状态） |
| `scan_reports` | 每次扫描的报告汇总 |
| `governance_plans` | 治理方案（check 列表、执行状态） |
| `prediagnosis` | 预诊断结果 |

`risk_findings.evidence` 是个重要设计——每条风险都带着**算出它的原始数值**，这样：
- 模型生成治理方案时可以直接用，不必重查
- 用户能看到判定依据
- 事实核对时这些数值有出处

#### 8.4.4 Harness 自身（3 张）

| 表 | 存什么 | 用途 |
|---|---|---|
| `chat_messages` | 会话消息 | 对话历史 |
| `agent_memory` | 长期记忆 | 按意图选择性落库，跨会话复用 |
| `agent_audit` | 审计日志 | 「这条变更是谁批准的」（含 `reason_type`） |

### 8.5 二十二种 SSE 事件

SSE（Server-Sent Events）= 服务器单向流式推送。Agent 每做一件事就推一个事件，前端实时渲染。

**权威清单在 `frontend/src/types/index.ts` 的 `ChatEventType`**。

#### 8.5.1 基础流程（10 种）

| 事件 | 什么时候发 | 前端怎么用 |
|---|---|---|
| `intent` | 意图识别完成 | 显示「识别为：故障定位」 |
| `agent_start` | 选定 Agent 开始干活 | 显示「DiagnoseAgent 接手」 |
| `phase` | 多阶段编排进入某阶段 | `full_checkup` 的阶段进度 |
| `phase_result` | 某阶段完成 | 阶段小结 |
| `thinking` | 模型输出了思考文本 | 显示推理过程 |
| `tool_call` | 要调某个工具 | 工具时间线上加一行 |
| `tool_result` | 工具返回了 | 时间线那行补上结果 |
| `answer` | 最终回答 | 主消息体 |
| `error` | 出错了 | 红色提示 |
| `done` | 整轮结束 | 停止 loading |

#### 8.5.2 可中断与自愈（4 种）

| 事件 | 什么时候发 | 前端怎么用 |
|---|---|---|
| `aborted` | 用户中断 / 超预算 | 「⏹️ 已中断：原因」（但若已有 partial answer 就不覆盖） |
| `compacted` | 上下文紧急压缩后重试 | 提示「已压缩上下文」 |
| `model_fallback` | 主模型不可用，已降级 | 提示「已降级到快模型」 |
| `usage` | 每步的 token 用量与耗时 | 累计成本显示 |

#### 8.5.3 权限门禁（3 种）

| 事件 | 什么时候发 | 前端怎么用 |
|---|---|---|
| `permission_request` | 危险操作需确认 | **弹确认卡片**（含工具名、参数、风险说明） |
| `permission_expiring` | 确认即将超时 | 卡片上倒计时提醒 |
| `permission_granted` | 已批准 | 卡片变成「已批准」 |

#### 8.5.4 子 Agent（2 种）

| 事件 | 什么时候发 | 前端怎么用 |
|---|---|---|
| `subagent_start` | 派发子 Agent | 时间线上开一个可折叠的子块 |
| `subagent_done` | 子 Agent 完成 | 子块显示状态（ok/error/aborted）与结论 |

> 子 Agent 内部的事件只**透传几类**（`agent_start` / `thinking` / `tool_call` / `tool_result`），避免把子的原始工具结果全灌进前端时间线。

#### 8.5.5 任务清单与续跑（2 种）

| 事件 | 什么时候发 | 前端怎么用 |
|---|---|---|
| `plan_update` | 模型更新了任务清单 | 渲染带勾选状态的清单 |
| `continued` | 步数用尽但任务未完成，已交接并开新一段 | 提示「继续执行第 N 段」 |

> `plan_update` 曾经**走旁路**发送，导致真机 4 次调用前端 **0 个事件**。改走主通道 yield 才修好。

#### 8.5.6 事实核对（1 种）

| 事件 | 什么时候发 | 前端怎么用 |
|---|---|---|
| `verify_warning` | 回答里有未在工具结果中出现的 traceID / 资源名 | 回答上方黄条，列出「说的 vs 最接近的真实项」 |

## 9. 被管环境：世界状态模拟器

> 为什么要自建：需要一个**可复现、可注入故障、且治理动作能真实生效**的环境来验证闭环。真实生产集群无法随意注入故障，静态数据集又无法体现「治理 → 恢复」的因果。

### 9.1 世界定义（`world_def.py`）

**300 服务** + 2×RDS + Redis、**603 实例**、**100 节点**、**74 接口**、**412 条边**，**预埋缺陷 + 阈值对照表**（`/control/threshold_table` 作为验收基准）。核心 8 服务手写、其余由 `_build_ext_specs()` / `_build_ext_apis()` 生成式扩展，扩容须守超卖率 166.7%±2、零新增预埋缺陷、新接口后端避开场景真值实体三条硬约束。

### 9.2 状态机（`engine.py`）

5 秒一拍，每个指标 = **基线 + 噪声 + 故障效应 + 动作效应**。

### 9.3 故障注入与传播（`faults.py`）

4 类故障场景（如 `slow_query_storm`、`rds_conn_spike`）。**反向 BFS 传播**：沿调用链逆向影响上游，每跳衰减 ×0.6——模拟真实的故障扩散。

### 9.4 治理动作生效（`actions.py`）

动作传回后不是瞬间恢复，而是按**半衰期指数恢复**——这才让「指标自然回落」成为可观测的过程。

### 9.5 渲染层（`renderers/`）

把世界状态渲染成阿里云 CMS / SLS / K8s 的**真实接口格式**。K8s 快照由世界状态**单向派生**，保证一致性。

> 这个设计的意义：采集器面对的是「阿里云格式的接口」，所以**对接真实环境只需替换采集器的数据源客户端与治理工具实现**，Harness 层零改动。

## 10. 质量保障体系

### 10.1 350 项常驻用例，一条命令跑完

```bash
bash scripts/run_tests.sh
```

| 范围 | 项数 |
|---|---|
| backend（Harness 各机制 + Skill 对账 + schema 同步 + 评测判定自测） | 278 |
| mock_server（世界状态、故障传播、动作生效） | 17 |
| data_collector（双通道采集、高水位、留存） | 16 |
| frontend（`tsc --noEmit` + `build`） | — |
| **合计** | **311** |

附带**数据库隔离静态自检**：凡 import 了 db 模块的测试文件，必须显式隔离，防止误连线上库。

> 其中 `tests/test_eval_metrics.py`（10 项）是**评测判定逻辑自己的回归测试**。
> 为何连评测代码也要测：串报判定曾**把两份正确回答判成串报**，
> 让我得出错结论并写进报告 —— 启发式判定不配双向用例，就只是一个会说谎的数字。

### 10.2 变异测试：验证测试真的有拦截力

不满足于「测试通过」，而是**故意注入回归，看用例是否变红**。Skill 文档准确性的 8 类漂移全部被抓到，并借此发现 3 个真实问题：

- `dispatch_agent` 的 `SUBAGENT_TYPES` 硬编码漏了 capacity/dbops（**静默失效**）
- `realtime_metrics` 不在 `sql_query` 白名单
- `postmortem.md` 的示例与自身约定冲突

### 10.3 Skill 文档与代码常驻对账

Skill 里引用的工具参数名、表列名、evidence 键、故障场景名，全部锚到唯一权威来源（registry / `db.metadata` / AST 解析 `builtin.py` 与 `faults.py`）做常驻校验。

> 为什么必要：这类漂移**不会报错**，只会让模型静默犯错——比崩溃更危险。

### 10.4 真机实测抓到的、单测覆盖不到的缺陷

| 缺陷 | 后果 |
|---|---|
| 子 Agent token 不计入父预算 | 整轮开销可突破用户设定上限 |
| `plan_update` 走旁路 | 4 次调用 0 个事件，前端完全看不到 |
| 父 Agent 面对失败子 Agent 原样重试 | 白烧 40435 token |
| 面对空数据不收手 | 反复试探直到烧穿预算 |

> 教训：**并行/流式/预算这类机制，单测能验证逻辑，但只有真机能暴露语义错误。**

### 10.5 量化评测：不止于“能跑”，而是“跑出数字、数字又能反咬出缺陷”

在常驻单测之外，建了一套 **L1/L2/L3 三层量化评测**（`backend/eval/`），完整结论见
《[量化评测报告（最终版）](量化评测报告-最终版.md)》：

- **真值一律从运行中的 mock_server 取**，评测端不复制（复制必漂移）；判定机械可复现，
  判不准的指标就不做。
- **规则侧（L2，不使用大模型）**：12 个注入故障场景 P/R/F1 均 **100%**
  （tp=23 fp=0 fn=0）、实例定位 11/11、串报 0、负样本 0 误报。
- **调度对比**：model 自主编排 **6/6** 优于 intent 硬映射 **5/6**，据此定为默认调度。
- **评测最大的价值不是分数，是反咬出的缺陷**：共揭出 13+ 个真实缺陷，
  最严重的一个（`query_logs` 无时间窗口→把两小时前的日志当当前，导致排障结论
  系统性错误）修复后复测主根因从错变对，并直接催生了幻觉核对的**时效维度**。

#### 10.5.1 朴素基线对照：这套 Harness 到底带来了什么

读者真正想问的是「我自己拿大模型接上工具不就行了，凭什么用你这套」。所以设了
`HARNESS_PROFILE=naive` 对照臂：**同一个模型、同一批业务工具、同样步数上限、
同样环境描述，只剥离方法论准则 / 事实核对 / 并行取数 / 子 Agent / 分段续跑**，
公平性由 9 项常驻测试锁死（防止给基线少配工具把数字做好看）。

L3 四类复杂任务（多故障并发 / 长程多阶段 / 大数据量聚合 / 易诱发幻觉的精确数值）
在 603 实例规模下实测：

| 维度 | 结论 |
|---|---|
| 根因准确率 | **打平 4/4 vs 4/4** —— 旗舰模型自身已具备排障方法论，如实记为无增益 |
| 工具调用 | 完整臂中位 **-27%**（22→16 次）；四轮观测方向从未反转 |
| 排障耗时 | 中位 **-20%**（127s→102s）；⚠️ 方差极大（同场景四轮 407~1521s），不宜单独作卖点 |
| 数据时效可信度 | 遇到同类问题时完整臂 **3 处全部告知用户** vs 基线 **11 处全部静默交付** |
| 变更安全 | 基线拿着 4 个破坏性工具**无门禁、无审计**；完整臂须经四层门禁 + 用户确认 |
| 单次成本 | 完整臂 **¥2.09 > 基线 ¥1.81**（如实保留对己不利项） |

**这个「打平」是负结果，但我们选择如实写进报告** —— 它把卖点从站不住的
「准确率提升 N 个百分点」修正为可复现的「同等正确下更省调用 + 结论可信 + 变更可控」。

#### 10.5.2 规模回归验证：结论不是小规模上的偶然

19 个实例里挑对 1 个，随机猜也有不低的命中率。所以集群分两次扩容，每次重跑全部场景：

| 集群规模 | P / R / F1 | tp / fp / fn | 实例定位 | 串报 | 规则扫描耗时 |
|---|---|---|---|---|---|
| 19 实例（初始） | 100% / 100% / 100% | 23 / 0 / 0 | 11/11 | 0 | — |
| 51 实例 | 100% / **96%** / 98% | 22 / 0 / **1** | 11/11 | 0 | 0.03s |
| **603 实例（32 倍）** | **100% / 100% / 100%** | **23 / 0 / 0** | **11/11** | **0** | **0.05s** |

**规模扩大 32 倍，精度一项未降、扫描耗时仅从 0.03s 增至 0.05s。**
中间那 1 个漏报**不是系统漏报、是评测自己造的**（场景间回稳超时固定 150s 短于
规则窗口 300s，上一场景的 finding 残留在下一场景基线里），修成按窗口动态计算后归零。

扩容中一个**反直觉的坑**值得记下：第一次只扩服务不扩接口，结果 trace 里仍只有
8 个服务 —— 因为 trace 与访问日志是**按对外接口的流量**生成的，新服务没有对外
流量就不产生 span。于是「300 服务」只体现在指标与 K8s 快照上，**Agent 做调用链
推理时面对的仍是原来 8 个服务**。补 60 个接口后 trace 服务数 8→48、拓扑边 44→95。
教训：**声明规模前必须逐个取数路径实测实际覆盖对象数**，按实例采集的会自动等比
放大，按流量入口生成的不会。

> 这套评测刻意把“**评测自己的错**”与“系统的错”并列记录 —— 因为**指标出错比
> 系统出错更难发现、危害更大**。已累积四类判定缺陷（含一次把正确回答判成串报、
> 一次把守规矩的交付判成截断、一次因只匹配实体全名而把简称判成漏报，
> 后者差点产出「下降 25 个百分点」的错结论），每一类都补了双向回归测试。

### 11.2 已知边界（明确接受，非遗漏）

1. **事实核对不理解语义**：把 A 服务的 P99 说成 B 服务的（两个数都真实存在），字面核对抓不到。要解决需建立「数值 ↔ 来源实体」的结构化绑定，是独立的一块工程；用字面规则近似只会得到高误报的伪功能。
2. **B 类数值只提示不拦截**：这是**刻意的**——换算与推算是该鼓励的行为。
3. **CI 未经真实 runner 验证**：配置已就位、执行体经变异法验证，但受权限限制没跑过真实 pipeline。
4. **被管环境是自建模拟器**，不是真实生产集群。对接真实环境的改动面已收窄到采集器数据源客户端 + 治理工具实现。
5. **注入的故障仍是单点 / 三点并发**，不是生产里那种长链级联事故。扩容放大的是「候选池与干扰项密度」（Agent 需从 600 个 Pod 指标、95 条调用链边中定位），不是故障本身的复杂度 —— 对外表述须据此精确。
6. **单次耗时方差极大**（同场景四轮 407~1521s，3.7 倍）。故效率结论以「工具调用次数」为主指标，耗时仅作辅证并标注方差；任何「提速 N 倍」的说法都不成立。
7. **static 与 live 两种数据源的集群规模不同**：static 读 `data/data/*.json` 早期快照（8 服务 / 19 实例），未随扩容重新导出。所有评测与规模数字均指 live。
