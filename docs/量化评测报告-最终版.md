## 0. 一页结论

| 评测层 | 考察什么 | 关键结果 |
|---|---|---|
| **规则引擎侧** | 12 个注入故障场景下，风险规则能否准确报出该报的、且不误报 | **该报的全报了，报的全是对的**：23 次命中、**0 误报、0 漏报**（精确率/召回率/F1 均 100%）；故障实例定位 **11/11**；把同型的另一台机器误伤为故障源 **0 例**；“看似异常但实际正常”的场景 **0 误报** |
| **Agent 侧（简单查询）** | 能否把自然语言问题准确转成数据查询并答对数字 | 准确率 **5/5**；中位耗时 **4.7 秒**；未发现编造内容（**0/5**） |
| **Agent 侧（多步排障）** | 能否在故障注入后定位到正确的实例、故障机理、数据表 | 全部维度都答对 **6/6**（模型自主编排调度）；中位耗时 **38.9 秒** |
| **意图识别** | 请求分类准确率（仅离线降级路径使用） | **96.2%**（25/26） |
| **架构选型** | 两种顶层调度方式的 A/B 对比 | 模型自主编排 **6/6** 优于预制意图硬映射 **5/6** |
| **规模回归验证** | 集群从 19 扩到 **603 个实例**（32 倍）后，规则侧精度与扫描性能是否退化 | **精度一项未降**：P/R/F1 仍 100%（tp=23 fp=0 fn=0）、实例定位 11/11、串报 0；扫描耗时仅 **0.03s → 0.05s**。详见 §6.1.1 |
| **★ 与朴素基线对照**<br>（同模型同工具，仅去掉 Harness） | 相比「自己接个大模型 + 同一批工具」，这套 Harness 到底带来了什么 | 根因准确率 **打平**（603 实例规模下 4/4 vs 4/4）；工具调用中位 **-27%**（22→16 次）、排障耗时中位 **-20%**（⚠️ 方差大）；数据过期时完整版 **3 处全部告知**用户、基线 **11 处全部静默交付**；变更安全基线**完全没有这一层**。详见 §7 |

> 表中“**23 次命中、0 误报、0 漏报**”对应专业写法 `tp=23 fp=0 fn=0`：
> tp（true positive）= 该报且报对了的；fp（false positive）= 不该报却报了的（误报）；
> fn（false negative）= 该报却没报的（漏报）。详见 §1.2 术语表。

一句话：**规则侧是确定性的、满分；Agent 侧在受控故障场景下能稳定定位根因，代价是单次排障数十秒到数分钟的推理开销。**

> 而相比「不用本项目」的替代方案（同模型 + 同工具裸接），这套 Harness 的价值
> **不在答得更对，而在用更少的调用拿到同样正确的结论、在结论不可靠时明确说出来、
> 在动手改生产环境前必须先问过你**。这个结论与我们原本的预期不同，实测如此（§7）。

## 1. 术语表

读懂本报告需要的全部概念，共 12 个。

### 1.1 系统侧概念

| 术语 | 解释 |
|---|---|
| **Agent** | 这里指"能自己决定下一步做什么"的大模型程序。它拿到一句自然语言诉求后，自行选择调用哪些工具、查什么数据、何时给出结论，而不是按预先写好的流程执行。 |
| **工具（Tool）** | Agent 可以调用的函数，如"查指标"、"查日志"、"扫描风险"。工具的名字、参数、用途以一份结构化说明书（JSON Schema）交给大模型，由模型决定何时调用哪个——类似给人一份"有哪些按钮、每个按钮什么用"的清单，按哪个由它自己判断。 |
| **ReAct** | Agent 的一种工作范式："推理（Reason）→ 行动（Act）→ 观察结果 → 再推理"，循环直到得出结论。与"固定流程"的区别是：下一步查什么由模型即时决定。 |
| **子 Agent** | 主 Agent 可以派出的下级 Agent，有独立的上下文，只把最终结论回传。用途是隔离中间数据（例如翻上千条日志），避免污染主流程的上下文。 |
| **风险规则** | 用代码写死的确定性判定逻辑，例如"某数据库实例连接使用率超过 80% 就报警"。它不经过大模型，判定结果完全可复现。本项目有 13 类。 |
| **顶层调度** | 决定"一句用户请求交给谁处理"的那一层。本项目有两种实现，见下。 |
| **模型自主编排（`model` 调度）** | 不做请求分类，直接把请求交给一个持有全部工具的 Agent，由**大模型自己**决定调什么工具、要不要派子 Agent、并行还是串行。 |
| **预制意图硬映射（`intent` 调度）** | 先用大模型把请求分类到 9 个预先定义的"意图"（如"查数据"、"定位故障"），再按一张**人写死的映射表**选一个专职 Agent。 |

### 1.2 评测侧概念

| 术语 | 解释 |
|---|---|
| **真值（Ground Truth）** | 评测时用来对照的"标准答案"。例如注入了"订单库慢查询"这个故障，那么"该报哪几条规则、故障在哪个实例、哪张表"就是真值。**真值的可信度决定整个评测的可信度**。 |
| **tp / fp / fn** | 判定结果的三种情况。以"报警"为例：<br>· **tp**（真阳性）= 该报，也真的报了 ✅<br>· **fp**（假阳性）= 不该报，却报了 → **误报**（让人白忙）<br>· **fn**（假阴性）= 该报，却没报 → **漏报**（真故障被放过） |
| **精确率 / 召回率 / F1** | 用 tp/fp/fn 算出的三个标准指标：<br>· **精确率** = 报出来的里面有多少是对的（衡量误报）<br>· **召回率** = 该报的里面报出来了多少（衡量漏报）<br>· **F1** = 前两者的综合得分（两个都高才高，任一个很低就拉低）<br>三者都是 100% 意味着"该报的全报了，报的全是对的" |
| **微平均（micro-average）** | 多个场景汇总指标时的一种算法：把所有场景的 tp/fp/fn **先加总再算比率**。<br>对比：如果每个场景各算一个准确率再平均（宏平均），那么"只期望 1 条规则"的小场景会与"期望 4 条"的大场景权重相同，不合理 |
| **串报（cross-report）** | 本项目自定义的一个失败模式：故障发生在 A 实例，但 Agent 把**同型号的另一台 B 实例**也说成是故障原因。因为治理动作会打到被指名的实例上，串报意味着可能去改一台无辜的机器。 |
| **负样本（negative case）** | 故意构造的"看起来异常但实际没越过阈值"的场景，用来检验系统会不会**无病乱报**。只测正样本的评测会天然偏乐观。 |
| **幻觉核对（事实核对）** | 检查 Agent 回答里出现的标识符（如链路追踪 ID）、资源名、数值，是否真的出现在它调用工具看到过的内容里。凭空生成的会被报警。 |
| **中位数 vs 平均值** | 本报告的耗时/成本一律用**中位数**（排序后取中间那个值）。因为大模型服务的响应时间波动很大（实测同量级调用可差数倍），平均值容易被一次极端值带偏。 |

## 2. 被测对象与运行环境

### 2.1 被测系统

一个面向 Kubernetes 生产集群的对话式运维 Agent，完成五类任务：数据采集 → 服务拓扑梳理 → 风险扫描 → 故障根因定位 → 治理闭环。

技术构成（与评测直接相关的部分）：

| 组成 | 规模 | 说明 |
|---|---|---|
| 专职 Agent | 8 个 | 顶层 1 个编排 Agent + 7 个专科 Agent（其中 5 个可作为子 Agent 被派发） |
| 工具 | 22 个 | 按安全等级分类：只读 / 写业务数据 / 破坏性变更 |
| 风险规则 | 13 类 | 高可用 4 + 容量 4 + 数据库 2 + 接口 1 + 缓存 2 |
| 大模型 | 双档 | 主模型 `qwen3.8-max`（推理密集任务）+ 快模型 `qwen3.6-flash`（摘要等轻任务） |

### 2.2 被管环境：世界状态模拟器

评测**不在真实生产集群上做**（在真集群上人为注入故障不现实）。取而代之的是一个自研的**世界状态模拟器**——一个独立进程，它：

- 维护一个虚拟集群的连续状态：**100 个节点、300 个服务、603 个实例**、2 台 MySQL、1 台 Redis、**74 个接口**、**412 条依赖边**（其中 Agent 经 trace 可见的调用链 95 条边 / 48 个服务）；
  （规模刻意分两次扩到 32 倍，目的不是数字好看，而是**提高选错对象的概率** ——
  在 19 个实例里挑对 1 个和在 603 个里挑对 1 个难度完全不同，候选池太小时
  「实例定位 100%」的说服力有限。每次扩容都重跑全部 12 个场景，见 §6.1.1）
- 每 2 秒推进一"拍"（tick），按拍生成指标、日志、调用链数据，并以**阿里云可观测接口的格式**对外提供（云监控 CMS / 日志服务 SLS / K8s API）；
- 支持**按名字注入故障**：注入后指标按物理规律连续演变（例如连接数逐步爬升、下游服务被传导变慢），而不是把某个字段硬改成异常值；
- 支持**接收治理动作**：Agent 执行"加索引"、"升配实例"后，模拟器改变世界状态，指标自然回落。

> **为什么这一点对评测很重要**：如果故障是"把某个字段直接改成 95%"，那么 Agent 只要读到那个字段就赢了，评测就退化成了读数测试。模拟器让故障有传导链条（数据库慢 → 接口超时 → 错误率上升），Agent 必须真的沿链路推理。

### 2.3 数据链路

```
世界状态模拟器（:9001）             ← 虚拟集群，每 2 秒推进一拍
      ↓  阿里云格式接口（CMS / SLS / K8s）
采集进程                            ← 定时 60 秒（拓扑类）+ 实时 10 秒（水位类）双通道
      ↓  落库
数据库（17 张表）
      ↓
Agent 后端  ← 被测对象：规则引擎在这里跑，Agent 在这里调工具查库
```

评测脚本站在最外层：向模拟器注入故障 → 等采集与规则窗口 → 读规则输出、向 Agent 提问 → 按真值判定。

## 3. 真值从哪来（评测可信的前提）

这是整份报告最关键的一节。**评测结论的可信度上限，等于真值的可信度。**

### 3.1 三条真值来源

| 真值类型 | 来源 | 为什么可信 |
|---|---|---|
| **稳态预埋缺陷**（无故障时该报哪 7 条风险） | 模拟器的 `/control/threshold_table` 接口暴露的 `planted_defects` | 这 7 个缺陷是**构造世界时刻意埋进配置里的**（如"订单服务只有 1 个副本"、"支付服务 3 副本全在同一可用区"），不是事后标注的 |
| **故障场景真值**（注入某故障后该报哪些规则、故障在哪个实例/哪张表） | 模拟器的 `/control/scenarios` 接口 | 每个场景的定义里直接写着 `expected_rules`、`expected_instance`、`expected_table`，与故障的注入逻辑写在同一处 |
| **数据查询真值**（"当前有几条未治理风险"这类问题的答案） | **评测时当场执行 SQL 从数据库算出来** | 不预先写死答案。数据库里的数据每分钟在变，写死的答案必然过期 |

### 3.2 一条铁律：真值只从运行中的系统取，评测端绝不复制

评测脚本**不在自己的代码里抄一份场景定义**，而是每次运行时通过 HTTP 从模拟器拉取：

```python
raw = httpx.get(f"{MOCK}/control/scenarios").json()      # 真值从运行中的环境取
scen = {it["id"]: it for it in raw["scenarios"]}
```

> **为什么**：一旦评测端复制一份真值，两边就会漂移——有人改了故障定义，评测还在用旧的标准答案判对错，得出的结论看起来正常却完全错误。这类错误比"评测报错"危险得多，因为它不会被发现。

### 3.3 另一条铁律：判定必须机械可复现；判不准的指标就不做

所有判定都是确定性的字符串/数值比对，不使用"让另一个大模型评分"（LLM-as-judge）——那样每次跑分数都不一样，无法用来判断改动是变好还是变坏。

以下内容**刻意不评测**，因为没有可复现的判定口径：

- 回答的"表达质量"、"是否完整"、"专业程度"；
- **人工排障耗时对照组**——没有真人计时数据。报告中出现的"提速 N 倍"一律标注为按明示假设的估算，不作为结论。

## 4. 评测数据

评测分两层：**L1 不需要注入故障**（跑完就有数字），**L2 需要注入故障**（更贵但更接近真实排障）。

### 4.1 L1 数据（26 + 5 + 1 条）

| 数据集 | 规模 | 内容 |
|---|---|---|
| 意图用例 | **26 条** | 人工标注的"请求 → 应属意图"对照，覆盖全部 9 类意图 |
| 数据查询用例 | **5 条** | 纯计数类问题，真值由 SQL 当场算。例："当前 open 状态的风险有几条？只回答条数" |
| 稳定性用例 | **1 条 × 3 次** | 同一个问题连续问 3 次，看结论是否一致 |

数据查询用例刻意都选**只回答一个数字**的问题——这样判定可以做到完全机械（回答里有没有那个数），不涉及对表述的主观评价。

### 4.2 L2 数据：12 个故障场景

场景不是随手编的，是按**四种考察目的**设计的：

| 考察目的 | 场景举例 | 为什么需要 |
|---|---|---|
| **基础定位** | 订单库连接打满、慢查询风暴、Pod 内存溢出重启 | 最基本的能力：故障在哪 |
| **同型不同实例**（2 组） | `core_db_conn_exhausted`：两台同型号 MySQL，故障只在 core 库 | 检验会不会把无辜的另一台也报进去（串报） |
| **易混淆对**（2 组） | `redis_cache_avalanche`（缓存雪崩）vs 数据库故障——表层现象几乎一样（接口变慢、后端负载升高），但根因层不同 | 检验是"真的推理"还是"套模板"。缓存雪崩场景的正确答案要求指向 Redis，而不是被表象带到数据库 |
| **负样本**（1 个） | `memory_creep_no_breach`：内存缓慢上涨但**未越过阈值** | 检验会不会无病乱报。只测正样本的评测会天然偏乐观 |

难度分布：easy 4 个 / medium 5 个 / hard 3 个（难度是场景定义里的标注，反映需要几层推理）。

其中 2 个场景带**表级真值**（`slow_query_storm` → `orders` 表、`inventory_slow_query` → `inventory` 表），用于考察"能否精确到表"而不只是"说对了哪个数据库"。

### 4.3 附：13 类风险规则清单（看懂结果表里的规则编号）

结果节会出现 `DB-001`、`CACHE-002` 这类编号，对照此表阅读。
**P1 = 高优先级（影响可用性），P2 = 中优先级（影响稳定性或容量余量）**。

| 域 | 编号 | 级别 | 判定条件 |
|---|---|---|---|
| **HA** 高可用 | HA-001 | P1 | 多副本服务的实例全部落在同一可用区（该区故障则服务整体不可用，多副本白配） |
| | HA-002 | P1 | 服务只有 1 个副本（无冗余） |
| | HA-003 | P2 | 容器缺失存活/就绪探针（K8s 无法判断容器健康，挂了不重启） |
| | HA-004 | P2 | 缺失 PodDisruptionBudget（节点维护时可能一次驱逐全部副本） |
| **CAP** 容量 | CAP-001 | P1 | 容器缺失 CPU request（调度器无法为其预留算力） |
| | CAP-002 | P2 | 容器缺失内存 limit（内存失控会拖垮整个节点） |
| | CAP-003 | P1 | 命名空间 CPU 超卖率 > 150%（∑Pod 的 CPU limit ÷ ∑节点可分配量） |
| | CAP-004 | P2 | 数据库实例内存使用率 > 85% |
| **DB** 数据库 | DB-001 | P1 | 数据库连接使用率 > 80%（连接耗尽后新请求直接失败） |
| | DB-002 | P2 | 无索引慢查询：扫描行数 ≥ 100 万且返回行数 < 10（全表扫描特征） |
| **API** 接口 | API-001 | P1 | 接口 P99 延迟 > 1 秒 或 错误率 > 1% |
| **CACHE** 缓存 | CACHE-001 | P1 | 缓存实例内存使用率 > 80%（接近上限会成批驱逐缓存，请求全量击穿到数据库） |
| | CACHE-002 | P1 | 缓存实例 CPU 使用率 > 70%（Redis 命令执行是单线程的，70% 已接近拐点） |

> **P99 延迟**：把所有请求按耗时排序，第 99% 位置的那个值。它比平均值更能反映"最慢的一小部分用户有多慢"。
>
> **为何缓存阈值（80%/70%）比数据库的（85%）更保守**：缓存是多个服务共享的依赖，
> 一处失效会同时放大成多条链路的故障；而数据库内存高主要是性能劣化。

在 live（实时）模式下，指标类规则都带**滑动时间窗口**（默认 5 分钟），且**按实例分组逐个判定** ——
后者很关键：世界里有 2 台 MySQL，不分组会把单实例的 95% 稀释成双实例均值 67% 而漏报。

## 5. 评测标准（每个指标怎么判）

### 5.0 先看一次完整的评测流程

以 L2（需注入故障）为例，一个场景的完整流程如下。每一步都是自动的，人不介入判定：

```
① 清场与回稳
   把模拟器里所有活跃故障恢复，轮询等到风险数回落到稳态的 7 条
   （上一场景的残留会被算进下一场的基线，必须等）
        ↓
② 取基线
   扫一次风险，记下当前开着的风险集合（规则编号 + 资源名）
        ↓
③ 注入故障
   POST /control/inject_fault {"scenario_id": "redis_cache_avalanche"}
   模拟器开始改变世界状态，指标沿调用链逐步传导
        ↓
④ 等待数据进入规则窗口（145 秒）
   采集进程把新数据写入数据库，直到滑动窗口内的均值真的越阈
        ↓
⑤ 再扫一次 → 与基线做差集 = 本次故障新增的风险
   与真值 expected_rules 对账 → 算 tp / fp / fn
   看 resource_ref 是否指向真值实例 → 实例定位、串报
        ↓
⑥ 向 Agent 提问（如需评测 Agent 侧）
   用通用问法，**刻意不告诉它是哪个组件出问题**（那等于把答案喂给它）：
   “线上有接口变慢或报错，帮我定位根因……”
   按 5.2 的四个维度判定回答，并保留回答全文
        ↓
⑦ 恢复故障，进入下一个场景
```

全程有三道**环境健康探测**（场景开始前、注入后扫描时、每次排障结束后）；
任一次探测到模拟器失联，整轮评测**立即终止并报错** —— 原因见 §7。

### 5.1 规则引擎侧

规则引擎不经过大模型，判定完全机械。

**基本思路：拍两张照片做对比**。注入故障前扫一次风险，得到一张"本来就有哪些风险"的清单（叫**基线**）；
注入后等数据进入规则的时间窗口，再扫一次得到新清单。
**两张清单相减（“差集”）就是本次故障新引起的风险** —— 只看新增的，旧有的不算。

> **先看懂三个字段名**（下表会用到，它们是场景真值里的标注）：
>
> | 字段 | 大白话 |
> |---|---|
> | `expected_rules` | 这个故障**应该报出哪几条规则** |
> | `resource_ref` | 一条风险**指向哪个具体对象**（哪台数据库 / 哪个服务 / 哪个接口） |
> | `must_not_flag_instance` | **不得被误伤的那台机器**（同型号的另一台，用于测串报） |

| 指标 | 判定口径 |
|---|---|
| 精确率 / 召回率 / F1 | 把"新增风险的规则编号"与真值 `expected_rules` 逐一对账。十一个正样本取**微平均**（定义见 §1.2） |
| 故障实例定位 | 新增风险的 `resource_ref` 是否指向真值实例。<br>**一处需要拐一下的地方**：接口类规则指向的是接口路径（如 `POST /api/orders`）而不是服务名，需要先查"这个接口由哪个服务提供"才能对上真值 |
| 串报 | 是否有风险落在 `must_not_flag_instance`（名单外那台无辜的机器）上 |
| 负样本 | 标记了"期望无新增"的场景，是否真的一条新风险都没报 |

**一处口径说明**：有些规则看的是"配置写得对不对"（如"只部署了 1 个副本"），
这类风险**在没注入故障时就已经在报了**（它们是构造世界时预埋的缺陷），注入故障不会让它们"新增"。
所以这类规则改判"当前是否仍在报"，而不是"是否新增" —— 否则会把正确行为记成漏报。

### 5.2 Agent 侧：根因定位四个维度分开判

刻意**不合成一个总分**。因为"定位准确率 70%"说明不了到底是找错了实例、还是实例对了但机理说错了——而这两种错的后果完全不同（前者会把治理动作打到无辜实例上，后者只是解释不到位）。

| 维度 | 判定口径 | 适用范围 |
|---|---|---|
| **实例定位** | 回答里是否出现真值实例名 | 所有正样本场景 |
| **机理关键词** | 是否说出了正确的因果机理词（如慢查询场景要出现"索引 / 全表扫描 / 慢查询"之一）。**否定语境不算命中**——回答"本次不是慢查询问题"虽然含"慢查询"，但它把机理说反了 | 标注了期望关键词的场景 |
| **表级定位** | 是否精确到真值数据表。**不能被同名服务假命中**——回答只提到 `inventory-service`（服务名）时，不能算成说对了 `inventory` 表 | 2 个慢查询场景 |
| **串报** | 是否把同型的另一台实例当成了当前根因。**区分"排除性说明"与"因果断言"**：写"此前 order 库故障已平息、风险项已 resolved"是正确的排除说明（不算串报）；写"触发源是 order 库上未治理的全表扫描"是因果断言（算串报） |
| **严格通过**<br>（代码里叫 `strict_ok`） | 上述维度中**该判的全部答对，且没有串报**——一票否决制。<br>"该判的"= 场景标注了什么就判什么：没标表级真值的场景，不会因为回答里没提数据表而被扣分（那是标注没要求，不是 Agent 的问题） | 综合口径 |

> **关于串报判定的说明**：这一项是启发式的（取实例名周围 ±80 字符的窗口，看是否出现排除性措辞或因果断言词）。因此：
> 1. 评测输出**保留每次回答的全文**，任何一项判定都可被人工复核；
> 2. 判定逻辑本身配有 **10 项双向回归测试**（既验证"真串报必须被抓到"，也验证"正确的排除说明不能被误判"）——启发式判定如果只往一个方向验证，放宽一次就会变成"永远及格"。

### 5.3 幻觉核对（贯穿所有 Agent 用例）

检查回答里的引用是否有出处，分四类、强度刻意不同：

| 类别 | 检查对象 | 判定 | 处置 |
|---|---|---|---|
| A1 | 链路追踪 ID 这类长十六进制串 | 不在"模型看过的内容"里 | **报警并要求 Agent 自我修正**（这类串不可能被推算出来，不在池中即为凭空生成） |
| A2 | 连字符资源名（如 `rds-mysql-order`） | 不在池中**且与池中某项只差 1~2 个字符** | **报警并自我修正**（只报"差一点就对"的，即典型的记错编号） |
| B | 关键数值 | 换算后仍不在池中 | **只统计不报警** —— 模型做单位换算（336500 微秒 → 336.5 毫秒）、求平均、四则运算都是应该鼓励的行为，硬拦截必然高误报 |
| C | 证据的**时效** | 某份工具结果的数据最新时间已超 30 分钟，而回答在描述"当前"状态 | **告警但不要求修正** —— 数据陈旧是取数窗口的问题，不是措辞问题，让模型重写解决不了 |

> **“模型看过的内容”到底指什么**：把本轮对话里模型真正读到过的文字全部汇总起来
> （系统提示词 + 用户问题 + 每一次工具返回的内容），从中抽出标识符、资源名、数值，
> 形成一个“它有权引用的东西”的集合（代码里叫**证据池**）。
> 逻辑很简单：**模型没看到过的东西，它说出来就是编的**。
>
> **A2 为何要加“只差 1~2 个字符”这个条件**（专业说法叫“编辑距离 ≤ 2”，
> 意思是改一两个字符就能变成真实名字）：若只判“不在池里就报警”会误伤大量正常表述 ——
> `read-only`、`blue-green` 这种英文词组也带连字符，但与任何真实资源名都相距很远；
> 而 `rds-mysql-03`（世界里只有 order/core 两台）与真实名字只差几个字符 —— 这才是典型的“记错编号”。

> C 类解决的是一个前三类看不见的盲区：**"模型看过的内容"是个没有时间概念的集合**。一条两小时前的日志与一分钟前的日志，在前三类检查里毫无区别。如果查询没带时间窗口、拿回了历史数据，Agent 会把它当成当前状况——而它引用的每一条数据都真实存在，A/B 类一声不响。

## 6. 评测结果

### 6.0 先看一个具体例子（一个场景从头到尾）

前面的判定标准比较抽象。这里用**缓存雪崩**这个场景完整跑一遍，体会一下评测到底在干什么。

**背景**：缓存（Redis）里大量数据同时过期，请求全部撑到后面的数据库上 ——
行业里叫“缓存雪崩”。它的阴险之处在于：**表面现象与数据库故障几乎一模一样**
（接口变慢 + 数据库负载升高），很容易把根因误定到数据库上。

| 步骤 | 具体发生了什么 |
|---|---|
| ① 真值是什么 | 模拟器的场景定义里写着：该报 `API-001`（接口慢）+ `CACHE-001`（缓存内存高）+ `CACHE-002`（缓存 CPU 高），故障实例是 `kvstore-redis-01` |
| ② 注入前基线 | 扫描到 7 条风险（全是预埋的配置缺陷，与本次故障无关） |
| ③ 注入故障 | 模拟器开始改变世界：Redis 内存 42% → 86%、CPU 16% → 78%；依赖缓存的三个服务因为缓存未命中而变慢，多个接口 P99 突破 1 秒 |
| ④ 等 145 秒 | 采集进程把新数据写入数据库，直到滑动窗口内的均值真的越过阈值 |
| ⑤ 再扫描 | 新增了 3 条风险：`API-001` `CACHE-001` `CACHE-002` —— 与真值完全一致（tp=3, fp=0, fn=0）；`resource_ref` 指向 `kvstore-redis-01`，实例定位 ✅ |
| ⑥ 问 Agent | 问法是通用的：“线上有接口变慢或报错，帮我定位根因”——**没有任何提示说问题在缓存** |
| ⑦ Agent 回答 | 它给出的根因是“`kvstore-redis-01` 缓存雪崩/集中失效引发回源风暴”，并指出它连带拉高了数据库连接数 |
| ⑧ 判定 | 实例定位 ✅（说对了是 Redis 而不是被表象带到数据库）；本场景未标表级真值与对照实例，所以那两项不判 → 严格通过 ✅ |

这个例子也说明了为什么要有“易混淆对”这类场景：**如果只看“接口慢了”就往数据库上猜，也能蒙对一半场景**；
只有把“根因在缓存”与“根因在数据库”的场景成对放进去，才能区分出“真的在推理”还是“在套模板”。

### 6.1.1 规模回归验证：规模扩大 12 倍后精度与性能是否退化

小规模上的满分是没有说服力的 —— 19 个实例里挑对 1 个，即使随机猜也有不低的
命中率。所以被管集群分两次扩容，每次都重跑全部 12 个场景：

| 集群规模 | 精确率 / 召回率 / F1 | tp / fp / fn | 实例定位 | 串报 | 规则扫描耗时 |
|---|---|---|---|---|---|
| 19 实例（初始） | 100% / 100% / 100% | 23 / 0 / 0 | 11/11 | 0 | — |
| 51 实例（3 倍） | 100% / **96%** / 98% | 22 / 0 / **1** | 11/11 | 0 | 0.03s |
| **603 实例（32 倍）** | **100% / 100% / 100%** | **23 / 0 / 0** | **11/11** | **0** | **0.05s** |

**结论：规模从 19 扩到 603 个实例（32 倍），精度一项未降、扫描耗时仅从
0.03s 增至 0.05s。**

中间那栏的 1 个漏报值得单独说明：**它不是系统漏报，是评测自己造的**。
当时场景间的"等待世界回稳"超时被设成固定 150s，而 live 模式下 finding 要靠
"窗口内的高值全部滑出"才会自然 resolved —— 规则窗口是 5 分钟（300s），
150s 根本等不到。于是上一场景的 API-001 残留在下一场景的基线里，
本场景报了也不算"新增"。修成按窗口动态计算后，这一轮 fn 归零（详见 §9.4）。

#### 扩容具体扩了什么（避免"规模"变成一个空数字）

扩容不是把服务数堆上去就算完，关键是**Agent 排障时真正面对的候选池有多大**。
第一次扩容（24 → 300 服务）后实测发现一个局限：trace 与访问日志是**按对外
接口的流量**生成的，而当时为保护 API-001 真值没有加接口，于是新增的 292 个
服务没有对外流量、不产生 span —— **Agent 做调用链推理时面对的仍是原来 8 个
服务**，"300 服务"只体现在指标与 K8s 快照上。补了 60 个对外接口后：

| Agent 排障时面对的对象 | 扩容前 | 扩容后 |
|---|---|---|
| 实例候选池（指标层） | 19 | **603 个实例** |
| K8s 配置对象 | 8 服务 | **300 Deployment / 600 Pod** |
| 调用链（trace 层） | 8 服务 / 44 边 | **48 服务 / 95 边** |
| 对外接口 | 15 | **74 个** |
| 指标维度数 | — | **702 个** |

附带效果：`build_topology` 单次返回从 2832 字符涨到 **16263 字符**，
已远超单工具结果预算（2000 字符）→ 触发落盘 + 预览 + 分页回取机制。
这让 §7 的"大数据量"维度对比有了**真实的物理来源**，而不再依赖模型自觉。

#### 扩容时被硬约束卡住的三处（都由 self_check 拦下）

1. **CPU 超卖率必须维持 166.7%±2**（CAP-003 的触发依据）。节点扩到 100 后
   分母变成 390,000m，若不同步补分子，超卖率会掉到 55%，CAP-003 直接失效。
   每 Pod 的 cpu limit 是**反算**出来的（390,000 × 166.8% = 650,520m 为目标
   分子）—— 先按估算值 966m 写过一版，实算只有 154.65%，被自检拦住。
2. **新增服务不得引入新的预埋缺陷**。292 个生成服务全部"配置健康"
   （有 cpu request / memory limit / 探针 / PDB / ≥2 副本且跨可用区），
   逐个核对确认，`PLANTED_DEFECTS` 仍是 7 条 —— 否则 7 条真值会变成一本乱账。
3. **新接口的后端服务不得是任何场景的 `expected_instance` /
   `must_not_flag_instance`**。否则新接口会在故障时产生 API-001、被判定归到
   那些实体上，制造出**假串报** —— 12 个场景的串报指标会凭空变差，
   而那是评测自己造的。新接口后端全部取自扩展服务，与禁用清单零交集。

### 6.3 Agent 侧：多步排障（含调度方式 A/B 对比）

| 表级定位 | 3/3 | 3/3 |
| **串报** | **0** | 1 次 |
| **耗时中位数** | **38.9 秒** | 47.2 秒 |
| 成本中位数 | ¥0.96 | ¥0.72 |
| 幻觉报警 | 1/6 | 1/6 |

逐场景（通过次数 / 耗时中位数）：

|---|---|---|
| `inventory_slow_query`（medium） | 3/3 · 44.0s | 3/3 · 36.4s |
| `core_db_conn_exhausted`（easy） | **3/3** · 35.9s | **2/3** · 64.9s |

**那一次失败的具体内容**（保留原文以便复核）：预制意图模式下有一次写出「触发源是 `rds-mysql-order` 上未治理的全表扫描」——它把同型的另一台数据库当成了当前故障的"触发源"。这是因果断言而非排除性说明，按 §5.2 的口径判为串报。模型自主编排的 3 次都没有把另一台牵连进因果链。

### 6.4 意图识别准确率

仅在离线降级路径（无大模型可用时）与前端标签展示中使用。

| 指标 | 结果 |
|---|---|
| 总体准确率 | **96.2%**（25/26） |
| 判错的 1 条 | 「当前 open 风险有几条」被分类为"风险扫描"，正解是"数据查询"（该问句含"风险"一词） |

> 补充实测：这条分类错误**没有导致回答错误**。在预制意图模式下该请求被路由到风险 Agent，风险 Agent 仍然正确回答了条数（数据查询准确率两种调度都是 5/5）。

### 6.5 结论稳定性

同一问题连续问 3 次，关键数字**三次一致**。

> 这一项考察的不是"答案对不对"，而是**同样输入是否给出同样结论**。Agent 的不确定性来自采样温度与工具调用顺序；一个连自己都无法复现的结论，在运维场景里没法作为决策依据。

### 6.6 排障耗时的参考对照（估算，非实测对照组）

**这一节的数字是按明示假设推算的，不是与真人对照的实测结果**，仅供理解量级。

推算模型：人工耗时 = 跨系统查询次数 × 单次查询耗时 + 系统切换成本 + 推断时间。以多步排障场景的实测均值（8 次工具调用、涉及 4 类系统）代入：

| 假设档位 | 单次查询耗时 | 推算人工耗时 | Agent 实测 | 比值 |
|---|---|---|---|---|
| 乐观 | 1.5 分钟 | 约 21 分钟 | 68 秒 | 18.7× |
| 中位 | 2.5 分钟 | 约 29 分钟 | 68 秒 | 25.8× |
| 保守 | 4.0 分钟 | 约 41 分钟 | 68 秒 | 36.4× |

> **简单查询类任务刻意不做这个推算**：人工打开控制台看一眼也就一两分钟，Agent 在这类任务上的价值是自然语言接口与免去记 SQL，不是速度。

## 7. 与朴素基线的对照：这套 Harness 到底带来了什么

前面 §6 全部在回答「它做得对不对」。但读者真正会问的是另一个问题：

> **我自己拿一个大模型接上云监控 API 不就行了？凭什么要用你这套 Harness？**

要回答它，必须有**对照组**。§6 那些"100%""6/6"都是绝对值，说不出"提升"——
提升是相对量，没有对照就无从谈起。

### 7.1 对照组怎么选，公平性边界划在哪

我们选的对照组叫**朴素基线**（配置项 `HARNESS_PROFILE=naive`），它代表
「不用本项目时最现实的替代方案」：同一个大模型 + 同一批运维工具，直接问。

**两臂之间必须只有一个变量，否则测出来的不是 Harness 的价值：**

| | 保留（两臂完全一致） | 剥离（这才是被测的东西） |
|---|---|---|
| 模型 | 同一个 `qwen3.8-max` | — |
| 业务工具 | 17 个，一个不减 | 4 个 Harness 专有工具（子 Agent、Skill 加载、任务清单、超长结果分页） |
| 步数上限 | 相同 | — |
| 环境描述 | 逐字相同（有哪些服务/库/缓存） | — |
| 方法论 | — | 9 条工作准则 + Skill 全文 |
| 机制 | — | 事实核对、并行取数、分段续跑、长期记忆 |

> **为什么环境描述要保留**：任何人裸接工具都会告诉模型"你管的集群长什么样"，
> 不给连工具参数都填不对——那是在造一个假对手，不是评测。
> 而工作准则（如"空结果本身就是结论""规则只是起点"）是本项目踩坑积累的，
> 那才是 Harness 的价值本体。

这条边界由 **9 项常驻测试**锁死（`tests/test_baseline_fairness.py`），
防止日后有人给基线少配一个工具、或往它的提示词里混进一句方法论——
那样数字会变好看，但已经不知道测的是什么了。

### 7.2 一个必须先讲清的前提：方法论不只在提示词里

实测后我们发现一件事，它决定了这份对照数字该怎么读：

**本项目的方法论沉淀，有相当一部分在工具层，而不在提示词层。** 例如
`query_logs` 的默认 30 分钟时间窗、`sql_query` 返回的数据时效标注、
工具描述里的引导、返回结构的设计。这些**两臂共享**（它们属于业务工具，
剥离就不公平了）。

所以本章测的是「**提示词方法论 + 事实核对 + 并行取数 + 子 Agent + 分段续跑**」
这一层的增量，**不是 Harness 的全部价值**。工具层的工程投入不在对照范围内。

### 7.3 结果一：根因定位准确率——打平

多轮实测，全部打平；**扩到 603 实例规模后重跑一轮，仍是 4/4 对 4/4**：

| 测试 | 复杂度维度 | 完整 Harness | 朴素基线 |
|---|---|---|---|
| 单故障排障（缓存雪崩） | 中 | 1/1 | 1/1 |
| 三故障并发（须分辨互相独立） | D3 强干扰 | 1/1 | 1/1 |
| 五段式全量体检 | D1 长任务 | 1/1 | 1/1 |
| 全量日志聚合（数千条按接口分组计数） | D2 大数据量 | 1/1 | 1/1 |
| 精确数值故障简报（须给准确水位+真 trace_id） | D4 易幻觉 | 1/1 | 1/1 |
| **合计** | | **4/4**（L3 四维度） | **4/4** |

**提升 0 个百分点（4/4 对 4/4）。** 这个结果与我们的预期相反，但它是实测的，
如实写在这里。连专门为「压垮基线」设计的 D4（要求大量精确数值、最易诱发编造）
上，基线也没有编造任何数字或 trace_id —— 因为 `qwen3.8-max` 本身就不编。

**为什么打平**，两个原因都要说：

1. **模型本身已经掌握了排障方法论。** 读基线的回答原文可见：它自己会用
   Trace 排除法否掉数据库、会把 Redis 指标突变的时间点与 503 爆发对齐、
   会用拓扑佐证（不依赖 Redis 的链路正常）、会明确区分三个故障互相独立。
   在 603 个实例、95 条调用链边、三故障并发这种难度下它依然不出错。
2. **工具层的引导两臂共享**（见 §7.2）。

> **这个结论本身是有价值的**：它告诉部署方，如果你用的是顶级推理模型、
> 且只做单次中等复杂度的排障，那么这套 Harness 的**准确率**收益接近 0。
> 该省的钱就该省——知道什么时候不需要一套东西，和知道什么时候需要一样重要。

#### ⚠️ 这个「打平」的结论差点被一处判定缺陷改写

603 实例那轮的原始输出是 **D3 上完整臂 0/1、基线 1/1**，汇总打印
「复杂场景上**下降 25 个百分点**」。查回答原文才发现是**判定的假阴性**：

| | 对 Redis 的观测 | 归类 |
|---|---|---|
| 完整臂 | 内存 87%、CPU 80% 尖峰、调用零错误、延迟 1.1ms | "只构成**风险**（CACHE-001/002），不是独立故障" |
| 基线 | 内存 87.8%、CPU 78%、调用零错误、延迟 1.1ms | "**故障三**：尚未爆炸的定时炸弹" |

两臂对事实的认定**逐项一致**（都发现水位飙升、都指出调用侧尚未受损、
都说与其他故障无因果关联），差别仅在**分类标签**（"风险项" vs "故障三"）
与**用词**（简称 "Redis" vs 全名 `kvstore-redis-01`）。
而判定只匹配全名字符串，于是把一份等价正确的回答判成漏报。

修法是给实体加别名表，但**同时要求实体名附近有异常语境词**——否则顺带提一句
"Redis 一切正常"也会被算成命中，判定就被放宽成了永远及格。
两个方向都用真机原文写成了常驻测试。

**这是同类问题的第四次**（串报判定 2 次、长任务截断 1 次，见 §9.4）。
共性是：**拿字符串匹配去近似语义判断，必然在措辞差异上翻车**。
它们无一例外都是"方向对自己有利或不利地系统性偏移"，
所以每次拿到反直觉的结论，第一步必须是回读回答原文、而不是直接写进报告。

### 7.4 结果二：效率——工具调用稳定更少，多数场景也更快

准确率打平，但**达到同样结果所用的工具调用次数，完整 Harness 一致更少**。
下表给出**两个集群规模各跑一轮**的结果（每轮都是同一次故障注入下两臂依次对比）：

| 指标（中位数） | 51 实例规模 |  | 603 实例规模 |  |
|---|---|---|---|---|
| | 基线 | 完整 | 基线 | 完整 |
| **工具调用次数** | 18 | **11**（-39%） | 22 | **16**（-27%） |
| 排障耗时 | 116s | **84s**（-28%） | 127s | **102s**（-20%） |
| 单次成本 | ¥1.61 | ¥1.68 | ¥1.81 | ¥2.09 |

**规模从 51 扩到 603 个实例后，效率优势依然存在**（工具 -27%、耗时 -20%），
且绝对差距变大（少 6 次调用 vs 少 7 次）。成本上完整臂始终略高，如实保留。

603 实例规模下的逐场景明细：

| 场景 | 基线工具 → 完整 | 基线耗时 → 完整 | 备注 |
|---|---|---|---|
| **D2 全量日志聚合** | 24 → **8** | 150s → **50s** | **3 倍差距**：完整臂 8 次工具 50 秒答对 5xx 总数与 Top4 接口分组 |
| D3 三故障并发 | 64 → **46** | 1276s → **635s** | 最复杂场景，完整臂快一半 |
| D4 精确数值简报 | 10 → **9** | 58s → **47s** | |
| D1 五段式体检 | 20 → 22 | 104s → **154s** | ⚠️ 本轮完整臂**更慢**（取证更充分的代价） |

工具调用更少的原因是**结构性的**：基线串行取数（并行是被剥离的机制之一）、
没有方法论引导，需要更多试探性查询才能收敛。机制细节见下一小节。

#### ⚠️ 耗时数字的一个重要限制：方差极大，不宜单独作为核心卖点

同一个 D3 场景、**同样的代码与配置**，四轮观测下完整臂的耗时是：

| 轮次 | 完整臂 D3 耗时 | 集群规模 |
|---|---|---|
| 第 1 轮 | 1521s | 51 实例 |
| 第 2 轮 | **407s** | 51 实例 |
| 第 3 轮 | 1440s | 51 实例 |
| 第 4 轮 | 635s | 603 实例 |

**407s 到 1521s，相差 3.7 倍。** 原因是 LLM Agent 的耗时同时受模型服务响应波动、
并行调度时序、以及模型每轮自选取数路径的影响。所以本报告的口径是：

- **"耗时中位 -20%~-28%" 可以引用**，但必须同时说明它来自单次观测的中位数、方差很大；
- **不写成"复杂任务提速 N 倍"** —— 51 实例那轮 D3 完整臂反而慢 63%，连方向都会翻转；
- **工具调用次数是更可靠的效率指标**：它反映结构性差异（并行 + 计划驱动的批量取数
  vs 串行回头重查），四轮下来完整臂中位稳定更少，从未反向。

> **一句话**：完整 Harness **稳定用更少的工具调用**做完同样正确的事，多数场景下也
> 更快；但**单次耗时波动大到不该作为核心卖点**，且在某些长任务上它可能因为取证
> 更充分而更慢。这个边界对部署决策比一句"提速 N 倍"有用得多。

#### 为什么能用更少的调用拿到同样正确的结论

这里要先破一个看似矛盾的直觉：**"完成一个排障任务所需的最小工具数是确定的，
凭什么 Harness 能更少？"** ——这个直觉本身没错，但它被真实数据推翻了前提。

以 D1 五段式体检为例，拆开两臂每一次工具调用（`update_plan` 是 Harness 专有的
任务清单工具，不算业务取数，单列）：

| 业务工具 | 完整 Harness | 朴素基线 | 基线多打 |
|---|---|---|---|
| build_topology | 1 | 1 | +0 |
| run_risk_scan | 1 | 1 | +0 |
| api_perf_stats | 1 | 1 | +0 |
| query_metrics | 1 | 2 | +1 |
| query_logs | 2 | 3 | +1 |
| sql_query | 2 | 3 | +1 |
| query_traces | 2 | 4 | +2 |
| **get_k8s_resource** | 1 | **5** | **+4** |
| **业务工具合计** | **11** | **20** | **+9** |

**关键观察：两臂用的工具种类完全相同（都是这 8 种），差距不在"种类"，
全在"重复次数"。** 基线多打的 9 次，没有一次是新工具，全是把同一个工具反复调。

所以你的直觉——"最小工具集是确定的"——是对的。真正的问题不是
"谁突破了最小值"（谁都没有，那不可能），而是**"谁在最小集之上产生的冗余更少"**：

- 理论下界（每种工具恰好一次、不重复、不试错）约 8 次；
- 完整 Harness 跑了 11 次，冗余 3 次；
- 朴素基线跑了 20 次，冗余 12 次。

Harness 不是"用低于最小值的调用完成任务"，而是**用三个机制把冗余压下去、
让实际调用更接近那个理论下界**：

1. **并行取数 vs 串行试探（最主要）**。完整臂遵循"多份互不依赖的只读数据，
   同一轮一次性发起"，一轮就把 metrics + logs + traces + 拓扑拿齐再判断；
   基线是串行的"查一个 → 看结果 → 再想查什么"，最典型的副作用就是**回头重查**
   —— 查完 trace 发现要对照 K8s 配置、查完 K8s 又要回看 metrics。
   `get_k8s_resource` 被打 5 次正是这么来的：不是一次拿全，而是想到一个查一个。

2. **任务清单强制"先规划再取数"**。完整臂第一步 `update_plan` 会逼它先想清楚
   "整个五段式体检总共需要哪些数据"，于是一次规划、批量取；基线走一步看一步，
   同一类数据分几次凑齐（`query_traces` 4 次、`sql_query` 3 次都是这个模式）。

3. **方法论准则替模型省掉试错**。完整臂的提示词有"空结果本身就是结论"这类准则，
   遇到空结果直接收手；基线没有，会换个写法再查一次确认，把本该一次结束的
   查询拖成两三次。

**但"调用更少"绝不等于"总开销更小"**（这正是上面 §7.4 那半节的要点）：完整臂
每次调用**更重** —— 并行一轮塞了多个工具、还带着更长的提示词（方法论 + Skill +
事实核对）。所以它省的是**往返次数**（每次往返都有固定的推理开销与试错风险），
代价是**每次往返更贵**。任务越复杂、需要的往返越多，省往返越划算；任务越简单，
重往返的固定成本越收不回 —— 这就是"越复杂越划算、越简单越是负担"的微观解释。

> **一句话**：完整 Harness **总是用更少的工具调用**做完事，但"更少调用"不等于
> "更快更省"——它每一步想得更多、取证更全。**任务越复杂，这套开销越划算；
> 任务越简单，越是纯负担。** 这个边界对部署决策比一句"提速 N 倍"有用得多。

### 7.5 结果三：可信度——差距最实在的地方

这里要先分清两类完全不同的问题，混在一起统计会同时误导两个方向：

- **A 类幻觉**：回答里出现了编造的 traceID / 资源名 → **回答本身错了**；
- **C 类数据时效**：回答没有编造任何东西，但它引用的数据已经过期
  → **回答没错，但结论的数据底座已经不适用了**。

长任务里早期查的数据到出结论时可能已经过期。**603 实例规模**下的四维度实测
（同一次注入、两臂依次对比）：

| | A 类幻觉（编造标识符/资源名） | C 类数据时效问题 | **是否告知用户** |
|---|---|---|---|
| 完整 Harness | 0 | 3 处 | ✅ **3 处全部告警/自动复核** |
| 朴素基线 | 0 | **11 处** | ❌ **0 处，全部静默交付** |

三点都要说清：

1. **A 类幻觉两臂都是 0**——旗舰模型在有真实工具结果兜底时不编造，
   核对机制在这个模型上没能拦下任何 A 类问题（它本来也没有）。这一项如实记为无差异。
2. **C 类时效差距是本对照里最实在的一条，且随规模扩大而扩大**：
   51 实例规模那轮是 4 处 vs 6 处，扩到 603 实例后变成 **3 处 vs 11 处** ——
   数据量更大、排障链路更长，基线手里的数据更容易放旧，而它**一处都不会说**。
   基线那 11 处是用同一套核对逻辑离线量出来的：它没有核对机制，
   这些问题不会被拦下，用户拿到的是一份"看起来完全正常"、
   实则部分结论建立在过期数据上的报告。
3. **这个对比比"完整臂 0 处问题"更有说服力**：它不依赖"完整臂恰好没遇到过期数据"
   这种运气，而是直接比较**遇到同类问题时两者的处置差异** ——
   完整臂 3 处全告知，基线 11 处全静默。

此外，Harness 侧还做了两项针对性改造（详见 §7.8 机制清单）：
- **给聚合型工具补数据时间窗**：`query_metrics` / `api_perf_stats` / `get_risk_report`
  原本返回纯聚合值（`points:120, avg:55.3`）、**一个时间戳都没有**，
  模型看不到数据新鲜度、核对器也无从判断。补上 `data_from`/`data_to` 后，
  模型开始在回答里主动标注数据窗口。
- **过期即自动重查复核**：检测到 C 类后自动带工具重新取数、逐项比对新旧结论
  （变了写"初判 X → 复核后 Y"，没变也明说"已用最新数据复核，结论不变"），
  并有次数/步数上限；重查后仍陈旧（如采集器停更）则如实降级为告警。
  603 实例那轮的 D3 就实际触发了一次：复核后把"慢日志 528 条"更新为
  **919 条**（9 分钟新增 391 条）并明确标注"仍在进行中且在恶化"。

> 生产环境里，一个基于半小时前数据、却在描述"当前状态"的结论，
> 足以让人按错误的现状去做决策。**两臂都会碰到这个问题，区别在于会不会告诉你。**

### 7.6 结果四：变更安全——基线完全没有这一层

这一项不需要评测就能说清，它是**设计事实**而非统计结果：

朴素基线拿到的是同一批工具，其中包含 4 个破坏性动作
（改副本数、建索引、升配实例、建 PDB）。它没有三态权限门禁、
没有白名单、没有审计留痕——**模型决定执行，动作就会发生**。

完整 Harness 下，同样的动作要经过四层门禁，并且必须拿到用户明确确认。
§7.3 那次五段式体检里，完整臂的结尾是这样的：

> 以上治理动作**尚未执行**。是否确认？建议先执行第 1、2 项，我逐项操作。

（顺带一说：这句话曾让我们的评测判定误判——把"守规矩"读成了"没做完"，
详见 §8.4。）

### 7.7 本章结论

| 维度 | 结论 | 数据强度 |
|---|---|---|
| 根因定位准确率 | **打平**（0 个百分点） | 3 轮实测，样本小 |
| 工具调用效率 | 中位 **-27%~-39%**（603 实例规模 22→16、51 实例规模 18→11），四轮观测方向从未反转 | L3 四维度实测 |
| 排障耗时 | 中位 **-20%~-28%**，多数场景更快 | L3 实测，⚠️ 方差大（同场景 407~1521s） |
| 部分长任务 | 可能**更慢**（取证更充分的代价，方向随轮次翻转） | L3 实测 |
| 数据时效可信度 | 遇到同类问题时：完整 **3 处全部告知**用户 vs 基线 **11 处全部静默交付**（差距随规模扩大） | L3 四维度，603 实例规模 |
| 变更安全 | 基线无门禁、无审计 | 设计事实 |

**一句话**：在顶级推理模型上，这套 Harness 的价值不在"答得更对"，
而在**用更少的调用把同样正确的结论拿到手，并且在结论不可靠时明确说出来、
在动手改生产环境前必须先问过你**。

## 8. 如何复现

三条命令，分别对应三层评测。前置条件：模拟器与采集进程在运行。

```bash
# 前置：启动世界状态模拟器与采集进程
cd mock_server && TICK_INTERVAL_S=2 nohup ../backend/.venv/bin/python -m uvicorn app.main:app --port 9001 &
cd data_collector && nohup ../backend/.venv/bin/python -m collector.main &

# ① L1：意图识别 + 数据查询 + 稳定性（不需要注入故障）
cd backend && .venv/bin/python -m eval.run_l1 --json /tmp/l1.json

# ② L2 规则侧：12 个场景全量，只测规则不问 Agent（不烧大模型额度）
cd backend && RULE_WINDOW_MINUTES=2 .venv/bin/python -m eval.run_l2 \
    --no-agent --wait 145 --json /tmp/l2_rules.json

# ③ L2 Agent 侧：调度方式 A/B 对比，每种调度重复 3 次取中位数
cd backend && RULE_WINDOW_MINUTES=2 .venv/bin/python -m eval.run_l2 \
    --only inventory_slow_query,core_db_conn_exhausted \
    --compare-routing --repeat 3 --wait 145 --json /tmp/l2_agent.json
```

### 两个必须理解的参数约束

| 参数 | 约束 | 原因 |
|---|---|---|
| `RULE_WINDOW_MINUTES`（规则的时间窗口） | **不能 ≤ 1 分钟** | 指标采集是 60 秒一批。窗口与采集同频时，窗口内样本数会在 0 和 1 之间振荡；落在"0 样本"相位的那次扫描，所有指标类规则都会返回空——与"真的没有风险"无法区分 |
| `--wait`（注入后等待时长） | **必须 ≥ 窗口时长** | 规则算的是窗口内均值。窗口里残留的故障前低值会把均值稀释到阈值以下（例如缓存内存 42%→86%，若 3 分钟窗口里只有 1 分钟故障数据，均值仅 57%，不越阈）。此时的"漏报"是评测参数造成的，不是系统缺陷 |

### 评测自身的防错设计

| 机制 | 作用 |
|---|---|
| 环境失联检测 | 每个场景开始前、注入后扫描时、每次排障结束后各探测一次模拟器健康。失联则**立即终止整轮**并报错——而不是继续跑。因为 Agent 只读数据库，模拟器死掉后旧数据仍在，照样能算出指标，但世界已不再演变、注入的故障永不恢复，这些数字看起来正常却毫无意义 |
| 场景间回稳等待 | 上一个场景恢复后指标是指数衰减的。若不等回稳就进下一场，残留会被算进下一场的基线，压低召回率。评测采用轮询等待直到风险数回落到稳态的 7 条 |
| 开跑前清场 | 评测被中断时已注入的故障不会自动恢复。开跑前先把模拟器里所有活跃故障恢复并等待回稳，避免在多故障叠加的脏环境里产出假数据 |
| 判定逻辑自测 | 评测的启发式判定（串报、机理关键词、表级）配有 10 项双向回归测试，正例与反例都取自真机回答原文 |

## 9. 结果的适用边界

以下不是"待办事项"，而是**读这份报告的数字时必须同时知道的限定条件**。

### 8.1 被管环境是模拟器，不是真实生产集群

模拟器的世界是连续演变的、故障有传导链条，但它终究不含真实生产环境的噪声：真实集群里有无关的告警、有其他团队的变更、有指标采集抖动。规则的阈值与 Agent 的推理在真实噪声下会有不同表现。

### 8.2 规则只覆盖被预先想到的故障模式

13 类规则是人写死的。它们判定快、可复现、零成本，但只覆盖"有人想到过并且愿意写下来"的部分。消息队列积压、连接池耗尽、外部依赖限流、证书过期等，目前都没有对应规则。

因此**"规则没报"不等于"系统正常"**。系统对此的应对是把兜底放在 Agent 侧（提示词明确要求：规则命中是线索起点而非排查范围的边界；无规则覆盖的异常用"水位对比 / 时间对齐 / 拓扑位置"三步自行判断），但这条兜底本身**没有被量化评测覆盖**——它是设计约束，不是已验证的指标。

### 8.3 Agent 侧样本量有限

- 多步排障：2 个场景 × 2 种调度 × 3 次 = 12 次。这个量足以支撑"两种调度的准确率差异"（6/6 vs 5/6）与"耗时中位数"的比较，但**不足以给出置信区间**。
- 单次排障耗时 30 秒到 13 分钟不等，方差很大，主要受模型服务端响应波动影响（实测同量级调用耗时可相差数倍）。所以报告一律用**中位数**而非均值。
- 12 个故障场景的规则侧结果是全量的；Agent 侧只覆盖了其中 2 个（受单次排障耗时限制）。

### 8.4 部分判定是启发式的

机理关键词、表级定位、串报三项基于关键词与上下文窗口匹配，不是语义理解。它们的误差方向刻意选成"对 Agent 不利"（只有明确出现排除措辞才算排除，否则计为串报），并且：

- 评测输出保留回答全文，每一项判定都可人工复核；
- 判定逻辑本身有双向回归测试守着。

### 8.5 "提速 N 倍"是估算

§6.6 的人工耗时没有真人对照组，是按明示假设推算的。它只用于理解量级，不应作为结论引用。

### 8.6 成本数字依赖模型定价

花费按配置的单价估算（输入 ¥0.02 / 千 token，输出 ¥0.06 / 千 token）。

> **token（词元）**：大模型处理文字的最小计费单位。中文大致 1 个汉字 ≈ 1~2 个 token，英文 1 个单词 ≈ 1~2 个。模型读入的内容（输入）与生成的内容（输出）分别计费，输出通常更贵。

这个数字用于横向比较不同方案的相对开销，**不等于真实账单金额**（实际计费还取决于服务商的具体策略）。
