## 0. 一句话结论

**规则引擎侧质量很高**（12 场景 P/R/F1 均 100%，零串报、负样本零误报）；
**Agent 排障侧在新旧两种调度下根因定位均 3/3**（§6.5），但耗时与成本仍偏高。

更值得看的是过程产出：评测共揭出 **13 个真实缺陷**，其中最严重的一个会导致
排障结论系统性错误（§3.1）；同时**评测自己也错了（或存在假阳性）共 7 处**，
其中一次直接把我引向了错的优化方向（把两份正确回答判成串报，§6.6）。

> 这份报告刻意把“评测自己的错”与“系统的错”并列记录。
> 因为**指标出错比系统出错更糟**：系统出错会被指标发现，
> 指标出错会让人去修一个不存在的问题、并把本来对的行为改坏。

## 1. 评测能做到什么程度：真值从哪来

这个项目能做**有标准答案的自动评测**，不是靠人读结果打分。真值有三个来源，
全部来自被管环境（mock_server）自身的定义：

| 真值 | 内容 | 用途 |
|---|---|---|
| `PLANTED_DEFECTS` | 7 条稳态预埋缺陷（HA-001~004、CAP-001~003） | 稳态基线对账 |
| `SCENARIOS[*].expected_rules` | 每个故障场景**应当**触发哪些规则 | 风险扫描 P/R/F1 |
| `SCENARIOS[*].expected_instance` 等 | 根因实体、同型对照实例、精确到表的根因 | 定位精度、串报判定 |

**基线校验**（做任何评测之前必须先过这一关）：稳态下扫描输出 **7 条 open
findings，与 7 条预埋缺陷逐条一致，零误报零漏报**。基线不对，后面所有对账都没意义。

### 为评测扩充的故障场景：4 → 12

原有 4 个场景样本量不足、且都集中在 order 库与 order/payment 服务上，只覆盖
5 类规则。更关键的是缺少「现象相似但根因不同」的样本——那恰恰最能检验
Agent 是在推理还是在套模板。按三条原则扩充：

| 类型 | 场景 | 考察点 |
|---|---|---|
| **同型不同实例** | `core_db_conn_exhausted` | 与 `rds_conn_spike` 完全同型但换一台 RDS，测定位精度与**是否串报** |
| **同库不同表** | `inventory_slow_query` | 与 `slow_query_storm` 同库不同表，测根因能否精确到**表** |
| **易混淆** | `redis_cache_avalanche` | 表层现象与数据库故障一样，根因在缓存层 |
| **快失败 vs 慢失败** | `dependency_timeout` vs `instance_down` | P99 暴涨 vs P99 不涨纯错误率 |
| **非数据库归因** | `product_cpu_saturation` | 测是否习惯性把接口慢归给 DB |
| **非故障** | `traffic_surge` | 容量不足而非"坏了"，正确结论应指向扩容 |
| **负样本** | `memory_creep_no_breach` | 内存涨但未越阈，**正确行为是什么都不报** |

场景数值都按稳态基线手算，并有常驻用例
`test_every_scenario_actually_moves_the_world` 逐个注入验证真的越阈——
否则"看起来 12 个场景、实际只有 4 个有效"会让评测彻底失去意义。

### 2.3 那个覆盖空白：已补，但补的只是这一个空白

上一轮评测里 `redis_cache_avalanche` 的实例定位是 ❌，而那**不是判定错误，是真实的
规则覆盖空白**：DB-001 与 CAP-004 都基于 `acs_rds_dashboard` 命名空间，
当时的 11 类规则没有任何一条覆盖 Redis。所以缓存故障时规则只能报到接口层
（API-001，`resource_ref` 是接口路径），无法指向 Redis 本身。

**已补上两条缓存规则**（实测与验证过程见 §6.2）：

| 规则 | 阈值 | 稳态 | 雪崩时 |
|---|---|---|---|
| `CACHE-001` 缓存内存高水位 | >80% | 41.9% | 86.8% |
| `CACHE-002` 缓存 CPU 高水位 | >70%（单线程模型） | 17.9% | 77.5% |

> 没加第三条（连接数）：Redis 稳态连接使用率 18%、上限 10000，
> 现有任何场景都推不到阈值 —— 写了就是一条永不触发、也无法被评测验证的死规则，
> 只能把"规则条数"刷好看。

**但补规则解决不了“规则有限”这件事本身。**消息队列积压、连接池耗尽、
外部依赖限流、证书过期……仍然一条规则都没有。所以同时在 **Agent 侧**做了兜底：

| 层次 | 内容 | 位置 |
|---|---|---|
| 工作准则 | “规则没报不等于正常”、排查范围不受风险报告限制 | `agents/base.py` 准则 9 |
| 方法论 | 无规则覆盖时的通用三步：水位对比 / 时间对齐 / 拓扑位置 | `risk_governance` Skill「规则之外」 |
| 反向约束 | **规则命中也不等于它就是根因**（API-001 大多数时候是别人的症状） | 同上 |
| 沉淀 | 发现新模式后用 `create_risk_rule` 变成下次自动判定 | 同上 |

## 3. Agent 侧结果与发现的严重缺陷

### 3.1 ★ 最重要的发现：排障结论系统性错误（已修）

**现象**：在只注入 `redis_cache_avalanche` 的环境里，Agent 给出的结论是

> 「根因定位结论：orderdb 慢查询风暴打满连接池 + payment-service OOM +
> Redis 内存压力，**三源叠加**」

`traffic_surge` 场景同样如此（真值是流量突增，Agent 报「慢查询风暴 + OOM 叠加」）。
两次都把**不存在的故障**写进了根因。

**根因**：`query_logs` 的实现是

```sql
SELECT ... FROM app_logs WHERE 1=1 ... ORDER BY ts LIMIT :limit
```

既**没有任何时间窗口**，排序还是**升序**——返回的是库里**最旧**的日志。
实测：默认调用返回的是**距今 2 小时**的记录，正是前几轮评测注入
`slow_query_storm` / `pod_oom_crash` 的时间点。

**这个缺陷的危险之处**：

1. 结论完全错误，但**引用的每一条日志都真实存在** ——
   §3.3 的事实核对机制查不出来（数据确实在库里，只是时间不对）；
2. **单元测试覆盖不到** —— 测试数据都是刚写入的，不存在新旧混杂，
   升序与倒序取到的是同一批。只有在长期运行、库里积累了历史数据的
   真实条件下才会暴露；
3. 它同时解释了 Agent 为什么要跑那么多步：读到互相矛盾的证据后反复交叉验证。

**修复**：加默认时间窗口（`LOG_QUERY_DEFAULT_MINUTES=30`）、排序改倒序、
把窗口值一并回给模型（让它能分辨"没有"与"没查到"）、schema 暴露 `minutes`
参数（`0` 表示不限，兼容导出/审计）。常驻用例
`test_query_logs_returns_recent_not_oldest` 用"3 小时前 + 刚刚"两条日志钉住行为。

### 3.2 待优化：排障耗时与成本失控

| 场景 | 耗时 | 工具调用 | 成本 |
|---|---|---|---|
| `core_db_conn_exhausted` | 501 s | 39 次 | ¥6.74 |
| `redis_cache_avalanche` | **1352 s（22.5 分钟）** | **58 次** | **¥16.02** |
| `traffic_surge` | 496 s | 37 次 | ¥7.07 |

这是**预算熔断停用后的直接代价**（当前策略：让 Agent 跑到任务完成，暂不计成本）。
一次排障 22 分钟 / ¥16 在生产上不可接受。

需要说明：这三次都发生在 §3.1 缺陷**修复之前**——Agent 读到矛盾证据后反复
交叉验证，本身就会推高步数。修复后同场景复测降到 896 s / ¥9.60
（**−34% / −40%**，见 §6），但仍不可接受。

### 3.3 简单查询侧（L1，26 + 5 条用例）

| 指标 | 结果 | 口径 |
|---|---|---|
| **意图路由准确率** | **96.2%（25/26）** | 对照人工标注，全部走 LLM 路径无降级 |
| **数据查询准确率** | **100%（5/5）** | 真值由 SQL 当场算出 |
| **幻觉 A 类报警** | **0/5** | verifier 事实核对 |
| **结论稳定性** | **三次一致** | 同一问题重复 3 次 |
| 平均端到端耗时 | 11.1 s | 区间 7.1~13.6 s |
| 平均工具调用 | 1.2 次 | 区间 1~2 |
| 平均单次成本 | ¥0.2343 | 平均 11,469 tokens |

**唯一的路由错误值得单独说**：「当前 open 风险有几条」被判成 `risk_scan`
（期望 `data_query`）。这不只是分类错——`risk_scan` 会**触发一次全量扫描并写库**，
对一个只读计数请求来说是过度反应。改进方向是在意图提示词里明确区分
"问已有风险的数量/状态"与"要求执行扫描"。

## 4. 排障耗时对比：人工基线（**估算，非实测对照组**）

项目没有真人计时数据，任何"人工 45 分钟"的说法都只能是模型化推算。公式与假设
必须和结论一起给出：

```
人工分钟 = 工具调用次数 × 每次查询分钟 + 涉及系统数 × 切换开销 + 因果推断
```

模型只主张一件事：**Agent 的一次工具调用 ≈ 人工一次跨系统查询**——
这点站得住，因为工具本身就是照着人工查询路径设计的。每次查询的单价取决于
熟练度，所以只给区间。

**必须按任务类型分档**（这是第一版评测踩的坑，见 §5）：

| 任务类型 | 人工基线 | Agent | 提速 |
|---|---|---|---|
| 简单数据查询（1.2 次调用） | 1.1~2.1 分钟 | 11.1 s | 6~11× |
| 多步排障（约 40 次调用） | 68~165 分钟 | 8~22 分钟 | 8~20× |

> ⚠️ **简单查询这一档不宜用来宣称提速**：人工打开控制台看一眼也就一两分钟，
> Agent 在这类任务上的价值是自然语言接口与免去记 SQL，**不是速度**。
> 真正体现耗时优势的是多步排障。

## 5. 评测自身踩的坑（会产出"看起来合理但完全错误"的数字）

这一节比结果本身更重要：**指标出错比系统出错更糟，它会把优化引向错误方向。**

| # | 坑 | 造成的假数字 | 修法 |
|---|---|---|---|
| 1 | **缺接口→服务映射** | API-001 的 `resource_ref` 是接口路径而非服务名，直接字符串匹配把 7 个正确结果判成未命中，"实例定位"虚报成 **36%** | 经 `world_status.apis.backend` 映射后回到 100% |
| 2 | **场景间污染** | 恢复故障后指标是**指数衰减**的，只 sleep 8 s 就进下一场景，残留被算进基线（实测基线从 7 涨到 11），recall 被系统性压低 | 轮询等待回稳（≤7 条）再取基线 |
| 3 | **中断残留** | 评测被 kill 时已注入的故障不会自动恢复。实测出现过基线 **17 条**、首个场景 **R=0%** 的假数据 | 开跑前清零所有 `active_faults` |
| 4 | **配置类规则口径错** | HA-*/CAP-001~003 稳态就存在，按"新增"判会把 `instance_down` 的 HA-002 记成漏报 | 这类规则改判"当前是否在报" |
| 5 | **真值本身漏标** | `slow_query_storm` 的 `mem_pct +18`（70%→88%）必然触发 CAP-004，但真值只写了 3 条，评测把一条**正确**告警算成误报（P 从 100% 掉到 75%） | 复核并补全真值 |
| 6 | **人工基线公式误用** | 对一句话查询也套"5 分钟因果推断 + 4 次系统切换"，算出「提速 **62×**」 | 按任务类型分档，见 §4 |
| 7 | **串报判定过严** | 排除性说明（"另一台 order 库正常"）被判成串报，窗口只有 ±40 字符 | 窗口放宽到 ±80、排除词 11→27 个 |
| 8 | **加速配置的副作用** | 把规则窗口从 5 分钟调到 1 分钟以加速评测，导致 9/15 接口样本不足被防抖跳过 → 假漏报 | 见下，这条反而查出了真缺陷 |

第 8 条值得展开：追查"为什么低流量接口不告警"时发现，API-001 的防抖阈值
`cnt < 20` 是**硬编码绝对值、不随窗口长度缩放**。默认 5 分钟窗口下合理，
但窗口调成 1 分钟后 **15 个接口里 9 个（60%）被静默跳过**，规则对它们彻底失效
且日志无任何提示。运维为了"更快发现问题"调小窗口，反而丢掉大半覆盖面。
已改为按窗口线性缩放（每分钟 4 个样本，**5 分钟仍为 20，生产行为不变**），
并对被跳过的接口打日志留痕——"规则没报"与"规则没跑"必须能分开。

## 6. 修复效果复测

修复 §3.1 之后，**用同一个场景（`redis_cache_avalanche`）原样重跑一遍**——
这是判断修复到底有没有用的唯一办法。

| 维度 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| **主根因** | 「orderdb 慢查询风暴 + payment-service OOM + Redis 内存压力，**三源叠加**」 | 「**kvstore-redis-01 缓存雪崩（热 key 集中失效→重建风暴）是当前持续劣化的主根因**」 | ❌ → ✅ |
| **历史 vs 当前** | 混为一谈，三者平级列为根因 | 明确分离：「慢查询风暴（**已停**）→ payment OOM（**已恢复**）→ Redis 雪崩（**当前仍在振荡**）」 | 显著改善 |
| 严格通过 | ✗ | **✓** | — |
| 耗时 | 1352.7 s | **896.6 s** | **−34%** |
| 工具调用 | 58 次 | 54 次 | −7% |
| 成本 | ¥16.02 | **¥9.60** | **−40%** |
| 幻觉 A 类报警 | 0 | 0 | — |

两点结论：

1. **修复解决了准确性问题**。Agent 不仅指对了主根因，还主动区分了"已停止的历史
   故障"与"当前仍在持续的故障"——这正是原缺陷剥夺它的能力（此前它看到的日志
   全部来自 2 小时前，无从判断时序）。
2. **耗时问题只被缓解，没有解决**。降低 34% 说明"读到矛盾证据后反复交叉验证"
   确实是原因之一，但 896 s / ¥9.6 仍不可接受。剩余部分来自预算熔断停用
   （当前既定策略）与五步排查法本身的步数，属于 §7 的待优化项 1。

## 6.2 本轮新增：顶层调度重构的实测（项 3）

### 改了什么

旧路径：用户请求 → LLM 意图分类（8 个预制意图）→ `INTENT_AGENT` 硬映射选一个 Agent，
全面体检另走写死的三阶段串行。两层都是人定的：意图覆盖不住真实请求（“先看拓扑
再对比两个库的水位”归不到任何一个），而“派几个 Agent、串行还是并行”也是写死的。

新路径（`AGENT_ROUTING=model`，默认）：不做意图分类，请求直接交给**编排 Agent**
（持有全部 21 个工具 + `dispatch_agent`），由模型自己判断。对齐 Claude Code 的做法
（它没有意图分类层）。旧路径保留为 `AGENT_ROUTING=intent`，为的就是能实测对比。

### 实测结果（`eval/_diag_routing.py`，事件流机械统计，不靠读回答判断）

用例：“先梳理一下服务拓扑，同时做一次风险扫描，两件事的结果一起给我”（跨两个预制意图）

| 模式 | 耗时 | tokens | 成本 | 实际行为 |
|---|---|---|---|---|
| model（提示词 v1） | 394.4s | 171482 | ¥7.0150 | 并行派 2 个子 Agent |
| **model（v2 修正后）** | **34.5s** | **28588** | **¥0.6385** | 自己并行调 2 个工具 |
| intent（旧硬路由） | 76.4s | 75946 | ¥1.7605 | DataAgent 串行 11 次调用 |

相比旧路由：**耗时 -55%、成本 -64%**，并行度仍为 2。
简单查询用例（“两个 MySQL 实例的连接使用率分别是多少”）：model 模式 **9.5s / ¥0.30**，
且**正确地没派子 Agent**（比 L1 基线 11.1s 略快 —— 省掉了意图分类那一跳）。

### ★ 最有价值的发现：提示词一处判断依据写错，差了 11 倍

v1 提示词把派子 Agent 的理由写成了并列两条：① 中间数据量大；② **子任务彼此独立**。
模型看到“两件事独立”就派了两个子 Agent —— 而第②条是错的引导：

> **独立性只决定能不能并行，不决定要不要派子 Agent。**
> 主 Agent 自己的工具调用本来就能并行（`concurrency_safe` + `_partition`），
> 而子 Agent 要重建一整套上下文、自己跑完整的多轮推理。

改成“派子 Agent 的唯一理由是中间数据多到会挤爆上下文”后，同一请求从 394.4s 降到 34.5s。

这条结论反过来修正了一个常见直觉：**“多 Agent 并行”不等于快。**
子 Agent 的价值是上下文隔离，代价是重复建立上下文 + 独立多轮；
真正的加速来自“同一轮里并行发多个工具调用”，而这个能力主 Agent 自己就有。

> 局限：每种模式每用例只跑了 1 次。之前已实测到同量级调用耗时可相差 7 倍
> （模型服务端波动），所以 34.5 vs 76.4 这一组具体数字不应当成稳定基准；
> 但 394 → 34.5（同一模式、仅改提示词）差距过大，不是波动能解释的。

## 6.3 本轮新增：事实核对的时间维度（项 4）

上一轮的待优化项 4：“引用的数据都真实存在，但不在当前窗口内”。
根因是证据池是个**无时间概念的集合**：两小时前的日志与一分钟前的日志没有任何区别。

新增 **C 类核对**：时间戳**按工具结果逐份记录**（而不是汇成全局区间）。
为何逐份：排障时常新旧数据混用（指标新、日志旧），只看全局最大时间会被新数据掩盖。

| 强度 | 处置 |
|---|---|
| 某份结果的数据最新时间 > 30 分钟前 | 记为陈旧源，告警并**指名是哪个工具** |
| 且回答在描述“当前/正在/目前” | 额外标 `time_risk` |
| 历史回顾语境（“两小时前那次演练”） | 仅记录时效，**不**标 time_risk |

**C 类不触发自纠正**：数据陈旧不是模型措辞的问题而是取数窗口的问题，
让模型重写既多花一次往返、也解决不了根本问题（它手里就只有旧数据）。

7 条回归用例覆盖，其中一条**直接还原了 §3.1 那个真实缺陷**（工具返回两小时前的日志 +
回答说“当前正在”），验证 A/B 类确实查不出、而 C 类能抓到。

> 附带收益：本轮评测中途遇到共享 RDS 被置只读（`read_only=ON`，写入报 1290），
> collector 连续失败 33 次、数据停更 6 分钟。这正属于 C 类能捕捉的情形 ——
> 以后数据停更不会再静默。

## 6.4 本轮新增：跑评测本身暴露的三个可靠性缺口

带 Agent 重跑 L2（项 4）时连着碰上三个问题，其中两个会直接产出**假数据**。

### ① mock_server 中途被杀，而评测毫无察觉地跑下去（★★★）

mock 日志正常服务到最后一条、无任何错误就停了（启动时漏了 `nohup`）。
而评测 **继续跑了下去**：Agent 只读数据库，旧数据还在，照样能算出 P/R/F1 与耗时 ——
但世界已不再演进、注入的故障也永远不会恢复，这些数字看起来正常却完全无意义。

**这比“评测报错”危险得多：报错会被看见，假数据会被当结论写进报告。**
已加 `_require_mock()`：场景开始前、注入后扫描时、**每次排障结束后**各探一次，
失联则抛 `EnvLost` 并**立即终止整轮**（不能当成“这个场景挂了”继续跑下一个）。

### ② LLM 客户端没设超时，且与外层重试叠加（★★）

`OpenAI(api_key=..., base_url=...)` 未传 `timeout` / `max_retries`，用的是 SDK 默认值
（600s 超时、重试 2 次）；而外层 `chat_with_retry` 自己还要重试 `LLM_MAX_ATTEMPTS` 次。
两层叠加后单次调用的最坏阻塞时长是 600 × 3 × 3 ≈ **1.5 小时**，
而阻塞期间 `run.abort` 根本检查不到（它只在每次 attempt 开头看一眼）——
**宣称的“可中断”在这段时间里是失效的**。

已改为显式 `timeout=LLM_TIMEOUT_S`（默认 180s）+ `max_retries=0`（SDK 不重试，
重试统一由 `chat_with_retry` 负责），最坏阻塞从 ≈1.5 小时降到 **540s**。

> ⚠️ 如实说明：这一修复目前只有**单测验证**（客户端 timeout=180s、max_retries=0）。
> 真机上并未观测到单次调用超时 —— hard 场景下 48 次调用平均 16.9s/次。
> 所以它是预防性加固，不是“修了一个正在发生的故障”。

### ③ 排障全程零进度输出 → 我自己误判卡死并中止了一轮评测（★★）

`_ask_agent()` 在整个排障期间不打印任何东西。而一次 hard 场景排障要 13 分钟，
于是外部看到的是：**11 分钟零输出 + CPU 0% + 一条 ESTABLISHED 连接**。
我据此判定“卡死”并中止了评测 —— **这是误判**：事后用 `sample` 看栈、
并从完成结果反推（48 次调用、平均 16.9s）可以确认它一直在正常多轮推理。

已给每次工具调用加上带时间戳的打点（含子 Agent 缩排），并把 `compacted` /
`model_fallback` / `continuation` / `aborted` 这四类影响可信度的事件一律打出来。

> 教训比修复本身重要：**一个跑十几分钟却不报进度的过程，等于把“正常”与“挂死”
> 渲染成同一个样子**。它不仅让人白等，还会诱导人做出错的处置（我就真的中止了）。

## 6.5 带 Agent 的调度对比：新旧两种调度的根因准确率

§6.2 只比了“拿到答案的开销”，没验证**答案对不对**。本节补上：
在**同一次故障注入下**依次用两种调度各排障一次（`--compare-routing`）——
分两轮跑会让两者面对不同的世界状态（指标是指数演变的），对比就不公平了。

### 结果（3 个代表性场景：hard / medium / easy）

> ⚠️ **本节数字经过一次修正**。首次报出的是“两种模式都 2/3、都在
> `core_db_conn_exhausted` 上串报”，并据此得出“串报是 Agent 推理层弱点”的结论。
> **那个结论是错的** —— 是串报判定的排除词表漏了“时态性排除”（详见 §6.6）。
> 下表是用修正后的判定重算的真实结果。

| | model | intent |
|---|---|---|
| 根因严格通过（该判维度全对且无串报） | **3/3 = 100%** | **3/3 = 100%** |
| 实例定位 | 3/3 | 3/3 |
| 表级定位 | 1/1 | 1/1 |
| 串报 | **0 例** | **0 例** |
| 平均耗时 | **448.8s**（96~809） | 748.5s（249~1246） |
| 平均成本 | **¥6.45** | ¥9.30 |
| 幻觉报警 | **1/3** | 3/3 |
| 派子 Agent | 0 次 | 0 次 |

逐场景：

| 场景 | model | intent |
|---|---|---|
| `redis_cache_avalanche`（hard） | ✅ 809.2s ¥9.445 | ✅ 750.6s ¥8.673 |
| `inventory_slow_query`（medium） | ✅ 96.5s ¥1.612 | ✅ 249.0s ¥2.744 |
| `core_db_conn_exhausted`（easy） | ✅ 440.7s ¥8.287 | ✅ 1245.8s ¥16.485 |

### 结论（按置信度排序）

1. **准确率完全持平且都是满分**（3/3 vs 3/3，实例定位 3/3 vs 3/3，串报 0 例）。
   把调度权从代码交给模型，**没有损害排障质量**。
2. **两种模式都正确区分了“当前病灶”与“已平息的历史故障”**：
   同型对照场景里两边都主动写了排除说明（“上一轮慢查询风暴平息、连接率已回落”），
   这比“只说对了哪台”更难 —— 它要求 Agent 在同一堆数据里分出时间先后。
3. **开销上 model 看似更优（-40% 耗时、-31% 成本），但这个结论置信度低**：
   方向并不一致 —— medium 场景 model 快 2.6 倍，而另一个 easy 场景
   （`rds_conn_spike`，单独跑的）是 intent 快（176.9s vs 253.7s）。
   四个场景里 model 赢 2 输 2。**在每场景 1 次的样本量下，开销差异无法与噪声区分。**
4. 幻觉报警 model 1/3 vs intent 3/3，差异明显但样本太小，只作为观察记录，不下结论。

### ★ 扩样本后的结论（每场景×3 次，取中位数）

上面的结论①②③④均基于每场景 1 次，样本量不足以下开销结论。扩到每场景 3 次后可以定论：

| | model (6 次) | intent (6 次) |
|---|---|---|
| 根因严格通过 | **6/6 = 100%** | 5/6 = 83% |
| 实例定位 | 6/6 | 6/6 |
| 表级定位 | 3/3 | 3/3 |
| 串报 | **0** | 1 (第 3 场景一次) |
| 耗时中位数 | **38.9s** | 47.2s |
| 成本中位数 | ¥0.96 | ¥0.72 |
| 幻觉报警 | 1/6 | 1/6 |

逐场景（通过次数 / 耗时中位数）：

| 场景 | model | intent |
|---|---|---|
| `inventory_slow_query`（medium） | 3/3 44.0s | 3/3 36.4s |
| `core_db_conn_exhausted`（easy） | **3/3 35.9s** | **2/3** 64.9s |

**intent 那次失败是真串报（不是评测误判）**：它写的是「触发源是 rds-mysql-order 上未治理的全表扫描」——
把 order 库当成了 core 库故障的“触发源”，这是因果推断而不是排除性说明。
model 3 次都没把 order 库牵连进因果链。

### 定论：确认 model 为默认调度

综合两轮实测（§6.2 的开销对比 + 本节的准确率对比），**确认 `AGENT_ROUTING=model` 为默认**：

| 维度 | model | intent |
|---|---|---|
| 根因准确率（扩样本） | **100%** (6/6) | 83% (5/6) |
| 简单查询（§6.2） | 34.5s / ¥0.64 | 76.4s / ¥1.76 |
| 意图分类开销 | 零（纯关键词） | 4.55s/条（快模型） |
| 同型实例区分 | 6/6 未串报 | 5/6，1 次把 order 库当成触发源 |

保留 `AGENT_ROUTING=intent` 的价值不是它更好，而是：(1) 无 LLM 时的降级归路；(2) 可对比基准。

### ★ C 类核对在真机上报了，而且报对了

这轮 4 次幻觉报警里，**3 次是新加的 C 类（数据时效）**，1 次是 A 类（编造 trace_id，
自纠正已触发并改对）。C 类报的内容：

```
sql_query 返回的数据最新只到 56 分钟前，而结论在描述当前状态   （model）
sql_query 返回的数据最新只到 69 分钟前，而结论在描述当前状态   （intent）
query_logs 返回的数据最新只到 32 分钟前，而结论在描述当前状态  （intent）
```

它暴露了 §3.1 那个缺陷的**未修补面**：`query_logs` 已经加了默认 30 分钟窗口，
但 **`sql_query` 是通用查询、没有任何时间约束** —— 模型直接查表时照样会把
一小时前的数据当成"当前状况"。

**已修**：`sql_query` 结果里最新一条数据旧于 10 分钟时，返回 `data_age_note`
明说时间跨度并提示加时间条件。**不强制加窗口** —— 查历史、做趋势对比都是正当用法，
但必须让模型知道自己手里是旧数据（与 query_logs 把窗口值回传是同一思路）。

> 这是一个完整的闭环：量化评测发现缺陷 → 加 C 类核对 → C 类在下一轮评测里
> 又揭出了同一缺陷我没想到的另一面。

## 6.6 ★ 一次典型的“指标自己错了”：串报判定把正确判成了错误

本节记录的不是被测系统的缺陷，而是**评测自己的缺陷** —— 以及它骗到了我。

### 发生了什么

§6.5 首次跑完后，`core_db_conn_exhausted` 场景上两种调度都被判为**串报**。
两个模式在同一个场景上同时失败，看起来是个很强的信号，于是我得出结论：

> “串报是 Agent 推理层面的弱点，与调度无关……这是下一步最值得改的点。”

这句话写进了报告、commit message、以及给用户的汇报。**它是错的。**

### 真相：Agent 写得很好，是判定看不懂

看两份回答的原文：

```
[model ] ⚠️ 附带观察：同一时刻 rds-mysql-order 连接率从 ~82% 回落到 ~55%
         （上一轮慢查询风暴平息），两个库呈“跷跷板”
[intent] （此前 rds-mysql-order 的全表扫描故障已平息：其连接率已回落至 ~55%，
         ……相关风险项已 resolved。）
```

两边都**明确把 order 库排除在当前根因之外**，而且还交代了它为何会出现在数据里
（上一轮演练的残留）—— 这是比“只说对哪台”**更好**的排障表述。

而串报判定的排除词表里没有“平息 / 回落 / 此前 / 上一轮 / resolved / 附带观察”
这一类**时态性排除**词，于是把它们当成了“把另一台也当成根因”。

### 修正与反向验证

补了时态排除词后立即出现**反方向误判**：

```
rds-mysql-order 连接率虽有回落，但它仍是本次故障的根因之一，需要一起治理。
```

这是真串报，却因为含“回落”而被放过。**放宽指标很容易把它改成“永远及格”。**
所以加了一道否决门：窗口里出现“仍是 / 根因之一 / 共同导致 / 一起治理”这类
**明确断言它是当前根因**的表述时，不论同句里有没有排除措辞，一律判为串报。

否决词选得很窄，刻意不收“仍有 / 两个库 / 同时”—— 真机回答里
“order 库**仍有** 843 条未治理慢查询”、“**两个库**呈跷跷板”都是正确的补充说明，
收进来就会把刚修好的误判又造回来。

### 根本原因：评测判定一条常驻测试都没有

这套判定决定报告里每一个 ✅ / ❌，却**从未被测过** —— 这就是它能连错两次的原因
（第一次是窗口 ±40 字符把对照说明切半）。已新建 `tests/test_eval_metrics.py`：

| 方向 | 用例 | 来源 |
|---|---|---|
| 真串报必须被抓到 | 4 条（并列根因 / 含排除词但断言仍是根因 / 裸提并建议一起治 / 共同导致） | 真机变体 |
| 正确排除不能误判 | 3 条（含 **2 条真机原文**） | 本轮评测 |
| 否决词不得过宽 | 断言 `仍有/两个库/同时/共同` 不在否决词表里 | 真机原文 |
| 串报必须否决 strict_ok | 1 条 | 口径不变式 |

### 这事的教训

报告里早就写着“**报告里的一个 ❌ 很贵 —— 会把优化引向不存在的问题**”（见 §7），
结果我自己就被两个 ❌ 引偏了：差一步就去改提示词“修”一个根本不存在的推理缺陷 ——
而那样做只会把本来很好的行为（主动区分当前病灶与历史故障）改坏。

**启发式判定必须配双向回归用例，否则它不是指标，只是一个会说谎的数字。**

### 后续：把同一标准补到其余启发式判定

串报判定修完后，按同一标准查了另外两个子串匹配的判定，各发现一个**假阳性**缺陷
（方向与串报相反：把没说对的判成说对了，使分数虚高）：

| 判定 | 假阳性缺陷 | 修法 |
|---|---|---|
| 机理关键词 `keyword_hit` | 回答“本次**不是慢查询**问题”把机理说反了，却因含“慢查询”被判命中 | 关键词紧邻前缀有否定词（不是/非/并非/排除）时不算命中 |
| 表级定位 `table_hit` | 回答只提 `inventory-service`（服务），`inventory` 表被子串假命中 | 表名后紧跟“-字母”（服务名形态）时跳过这一次 |

两者都**不改变已报的真机结论**（六份回答复判仍全部 strict_ok=True，且 inventory
场景确实说对了表名），只堵住假阳性通道。`tests/test_eval_metrics.py` 从 6 条扩到
**10 条**，两个新判定各配“正常命中 + 假阳性拒绝 + 真机结论不变”的双向用例。

### 评测自身也修了三处

- 负样本场景的“实例定位”本就不适用此判定（汇总已排除），单场景行却把它打印成 ❌；
- `--no-agent` 时根本没跑 Agent，难度分层却输出一片 `0/N`，看起来像“Agent 全错”；
- **串报判定把两份正确回答判成了错误**（§6.6）—— 这一条不仅是显示问题，
  它真的把我引到了错的优化方向上。

前两条不影响指标值，第三条直接改变了结论。**报告里的一个 ❌ 很贵** ——
会把优化引向不存在的问题。

### 局限（如实说明）

- **被管环境是自建的世界状态模拟器**，不是真实生产集群。规则与 Agent 的表现
  在真实数据的噪声下会有差异。
- **人工基线是估算**，没有真人对照组（§4）。
- Agent 侧样本量小（3~4 个场景做了完整排障），因为单次耗时 8~22 分钟；
  规则侧是全部 12 场景。
- 串报与"机理是否说对"的判定是**启发式的**，报告保留了回答全文以供复核。
