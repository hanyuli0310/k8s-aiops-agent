# 缓存域细则（CACHE-001 / CACHE-002）

这两条规则的由来值得先说：**它们是补的**。Redis 缓存雪崩故障第一次被评测时，
当时的 11 条规则里没有任何一条涉及缓存层，规则侧只报出了下游的 API-001（接口变慢），
根因一条都没报。所以读这一篇时请记住：**缓存域现在有规则了，但仍然是覆盖最薄的一域** ——
命中率、大 key、慢命令、连接风暴、集群分片倾斜，都还没有规则。

## CACHE-001 缓存实例内存使用率高水位（P1）

**判定**：窗口内内存使用率均值 > 80%（常量 `CACHE_MEM_THRESHOLD`）。

阈值比 RDS 的 85%（CAP-004）更保守，因为越阈后果不同量级：RDS 内存高主要是性能劣化；
缓存实例接近 maxmemory 会**成批驱逐 key**（或写入直接失败），命中率塔式下跌，
请求全量击穿到后端数据库。缓存是多服务共享依赖，一处失效会同时放大成多条链路故障。

**evidence 字段**

| 字段 | 实测值（雪崩场景） | 含义 |
|---|---|---|
| `memory_usage_avg_pct` | 86.8 | 窗口内均值（稳态 41.9） |
| `threshold_pct` | 80.0 | 判定阈值 |
| `window_minutes` | live 有值 / static 为 null | 统计窗口 |

## CACHE-002 缓存实例 CPU 使用率高水位（P1）

**判定**：窗口内 CPU 使用率均值 > 70%（常量 `CACHE_CPU_THRESHOLD`）。

阈值取 70% 而非 85%：Redis 命令执行是**单线程**的，CPU 到 70% 已接近拐点
（主线程排队、所有命令 RT 齐涨），等到 85% 时下游早已大面积超时。

**evidence 字段**

| 字段 | 实测值（雪崩场景） | 含义 |
|---|---|---|
| `cpu_usage_avg_pct` | 77.5 | 窗口内均值（稳态 17.9） |
| `threshold_pct` | 70.0 | 判定阈值 |
| `window_minutes` | live 有值 / static 为 null | 统计窗口 |

**两条同时报**基本可以确认是缓存雪崩/穿透类问题：内存被打满 → 驱逐 → 命中率崩 →
反复回源 → CPU 也被抬高。实测雪崩场景两条必然同时命中。

## ★ 最容易犯的错：把缓存故障判成数据库故障

缓存雪崩与数据库故障的**表层现象几乎一样**：多个接口 P99 破 1s、后端服务负载升高、
数据库压力上升。评测里 `redis_cache_avalanche` 与 `core_db_conn_exhausted`
就是刻意做成的易混淆对。鉴别方法：

| 观察点 | 缓存是根因 | 数据库是根因 |
|---|---|---|
| 变慢的服务范围 | **所有依赖该缓存的服务**同时变慢（user/product/payment） | 只有访问该库的服务变慢 |
| Trace 里最耗时的 span | 后端服务自身或 DB span 变多（回源次数暴增） | 单条 DB span 本身极慢 |
| 慢日志 | **没有新增慢查询**（SQL 本身没变慢，只是被调用次数变多） | 有 `rows_examined` 百万级的慢 SQL |
| 缓存实例水位 | 内存/CPU 双高 | 基本正常 |

**判别关键：慢日志是否新增。**缓存失效导致的数据库压力，是"同样的 SQL 被调用了十倍"，
而不是"SQL 变慢了"。用 `sql_query` 查 slow_logs 表（带时间窗条件），若窗口内无新增慢查询、
而数据库连接/CPU 却在涨，应优先怀疑缓存层，不要直接给"加索引"或"升配数据库"的建议。

## 治理能力的真实边界（必须如实告知用户）

本平台**没有缓存专用的治理动作**：没有清理大 key、没有调整 maxmemory-policy、
没有预热缓存、没有加分片。可用的只有 `upgrade_rds_instance`（它同时接受缓存实例）。

实测行为（`eval/_diag_upgrade_on_cache.py`）：

- `upgrade_rds_instance(instance_id="kvstore-redis-01")` **被接受**，
  实测 CPU 76.3→14.7、内存 87.0→41.1，水位回到稳态；
- `scale_out` 对缓存实例**直接失败**（`service not found`）—— 它只认 K8s 服务，
  不要对缓存实例调用它。

但**升配是治标**：雪崩的根因是缓存集中过期/命中率崩塌，扩容内存只是让驱逐来得晚一些。
给用户的建议里应当分开写：

1. **止血**（可立即执行）：升配实例，把水位压回安全区；
2. **治本**（本平台无对应工具，需人工介入）：过期时间加随机抖动避免集中失效、
   热点 key 预热、大 key 拆分、必要时加本地缓存二级兜底。

对第 2 类建议，明确说明"这些需要在业务侧改动，本平台无法自动执行"——
不要暗示存在一个能一键修复的工具。
