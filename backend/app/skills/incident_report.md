# 事件通报

通报和诊断报告**不是一回事**。诊断报告是给排查者看的（要证据链），
通报是给**不在现场的人**看的（要影响面和进展）。写通报时把证据细节压到最后。

## 五要素（缺任一都会被追问）

| 要素 | 内容 | 常见失误 |
|---|---|---|
| **影响面** | 哪个服务/接口、影响多少请求、用户侧表现 | 只说"order-service 异常"，没说用户下单会不会失败 |
| **当前状态** | 进行中 / 已缓解 / 已恢复 | 含糊说"在处理"，读者不知道现在还坏不坏 |
| **时间线** | 何时开始、何时发现、何时处置 | 缺"何时开始"——它决定影响时长的量级 |
| **已做/待做** | 已执行的动作与结果、下一步 | 只列已做，不说下一步谁负责 |
| **根因** | 一句话说清（细节放附录） | 一上来就是大段 SQL 与 span 分析 |

## 推荐结构

```markdown
## 【进行中】order-service 下单接口延迟劣化

**影响**：POST /api/orders P99 **1.244s**（正常 ≤0.39s），错误率 **1.78%**。
窗口内 1850 次请求，约 33 次失败。用户侧表现为下单卡顿、偶发失败。

**当前状态**：已定位根因，待执行治理（等待确认）。

**时间线**
- HH:MM  监控发现 P99 突增
- HH:MM  定位到 orders 表全表扫描慢查询
- HH:MM  提出索引方案，待确认执行

**根因**：`orders` 表缺 `(status, created_at)` 复合索引，
单次查询扫描 116 万行仅返回 7 行（比值约 16 万:1），占满 RDS 连接。

**已做**：完成根因定位，已核对 8 个接口确认仅此一个受影响。
**待做**：执行 `create_db_index`，复扫验证；预计 P99 回落至 0.4s 以内。

<details><summary>证据细节</summary>
（这里放 SQL、evidence 字段、span 耗时分布）
</details>
```

## 分级用词要克制

| 状态 | 用词 | 不要写 |
|---|---|---|
| 还在发生 | **进行中** | "疑似""可能有点问题" |
| 止血了但根因未除 | **已缓解** | "已解决"（根因还在，会复发） |
| 根因已治且复扫通过 | **已恢复** | 复扫未过就不能这么写 |

**"已缓解"和"已恢复"的区别必须守住**：升配 RDS 压下连接水位是缓解，
建完索引且 `run_risk_scan` 确认 resolved 才是恢复。写错会让人以为不用跟进了。

## 数字必须有出处

通报里的每个数字都应能追到工具返回：

- P99 / 错误率 → `api_perf_stats` 或 API-001 的 `evidence`
- 扫描行数 → DB-002 的 `evidence.min_rows_examined`
- 影响请求数 → `evidence.requests`

**不要估算或四舍五入到"大约几千"** —— 通报里的数字会被引用到复盘和汇报里，
含糊的数字比没有数字更糟。

## 影响时长怎么算

若数据里能拿到异常起始时间（日志按分钟分桶的突增点），就给出**具体时长**。
拿不到时**明确说"起始时间待确认"**，不要用"持续了一段时间"这种说法糊过去。

## 不要在通报里做的事

- 不写归因到人（"某某发布导致"）——通报讲事实，责任在复盘里讨论
- 不承诺没把握的恢复时间——写"执行后预计 X 分钟见效"而不是"X 分钟内恢复"
- 不省略"待做"——读者最关心的就是接下来会怎样
