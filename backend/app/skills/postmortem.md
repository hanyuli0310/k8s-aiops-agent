# 故障复盘

复盘的产出不是"我们知道了原因"，而是**下次能更快发现、或者根本不再发生**。
所以每份复盘必须落到**可验证的改进项**，否则只是一篇事后作文。

## 与通报的分工

| | 通报 | 复盘 |
|---|---|---|
| 时机 | 事件进行中 | 闭环之后 |
| 读者 | 需要知情的人 | 要改进的人 |
| 重点 | 影响面、当前状态 | 为什么会发生、为什么没早发现 |

## 结构

### 1. 时间线（用数据重建，不靠回忆）

```sql
-- 异常起始：按分钟分桶找突增点
SELECT ts / 60 * 60 AS bucket, COUNT(*) AS n
FROM app_logs WHERE level='ERROR' GROUP BY bucket ORDER BY bucket
```

时间线要标出四个关键点，并算出两个间隔：

| 关键点 | 怎么拿 |
|---|---|
| 故障开始 | 日志/指标突增的时刻 |
| 被发现 | 扫描报告首次出现该 finding（`risk_findings.scan_ts`） |
| 开始处置 | 第一个治理动作（`list_governance_actions`） |
| 恢复 | 复扫 resolved 的时刻 |

**发现耗时 = 被发现 − 开始** 和 **处置耗时 = 恢复 − 开始处置** 这两个数是复盘的核心指标。
发现耗时长说明监控有盲区，处置耗时长说明预案或工具不到位 —— 指向完全不同的改进项。

### 2. 根因（区分三个层次）

| 层次 | 示例 |
|---|---|
| 直接原因 | 接口 P99 超阈值 |
| 技术根因 | `orders` 表缺 `(status, created_at)` 索引，全表扫描 |
| 机制原因 | **上线前没有慢查询检查环节** |

**只写到技术根因是不够的。** 建完索引解决了这一次，但下一张表还会重犯。
机制原因才是改进项的来源。

### 3. 为什么没早发现（这一节最容易被跳过）

具体问：

- 有没有对应的监控规则？没有 → 改进项是加规则（可以直接 `create_risk_rule`）
- 规则有但阈值太松？→ 改进项是调阈值，并说明依据
- 规则命中了但没人看？→ 改进项是加通知渠道

这一节能直接产出可执行的动作，价值往往高于根因分析本身。

### 4. 改进项必须可验证

| 写法 | 评价 |
|---|---|
| "加强 SQL 审核" | ❌ 无法验证是否做到 |
| "给 `orders` 表加 `(status, created_at)` 索引" | ✅ 已完成，可查 |
| "新增 AI-002 规则：任何表出现 `rows_examined/rows_sent > 10000` 即告警" | ✅ 可用 `create_risk_rule` 落地并验证 |

每条改进项写清 **做什么 / 怎么验证 / 是否已完成**。做不到的就不要写进去。

## 沉淀进长期记忆

复盘结论应该变成**下次能被自动召回的资产**，而不是留在一次对话里。
`agent_memory` 的 `conclusion` scope 就是为此存在的：

- key 用**资源级标识**（如 `order-service` / `rds-mysql-01`），便于下次按资源命中
- content 写**一句话结论 + 关键数值**，不要长篇

例：`conclusion / orders-slow-query` →
"orders 表缺 (status,created_at) 索引导致全表扫描（116 万行:7 行），
已建索引，API-001 与 DB-001/002 同时 resolved"

下次再遇到 order 相关问题时这条会被召回，能直接跳过一轮排查。

## 复盘里不该出现的东西

- **归因到人**。复盘的目的是改机制，不是追责。
- **无数据支撑的推测**。拿不到时间线就说"起始时间无法确定"，不要编。
- **重复已有的改进项**。先用 `list_risk_rules` 看规则是不是已经有了。
